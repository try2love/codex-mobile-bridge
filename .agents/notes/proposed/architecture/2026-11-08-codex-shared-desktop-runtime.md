# Agent Note: Codex 共享原生运行时与侧边标签同步验收

Status: proposed

本提案的“必须自动关闭原 App 已打开标签”验收条件已由用户收窄；当前生产实现与数据删除验收见[共享接入的数据删除边界](../../implemented/architecture/2026-11-08-codex-shared-runtime-data-deletion.md)。本篇保留原提案和当时的界面同步证据，不表示该标签同步已实现。

## 问题

原 App 已持有父聊天时，另起元数据运行时执行原生侧边聊天创建或永久删除会被写入者锁拒绝。现有拒绝分类能够避免盲目重放，但不能满足原 App 与手机同时管理同一聊天的目标。

本提案部分替代[原生侧边聊天](../../implemented/feature/2026-11-07-native-attached-side-chats.md)中使用独立元数据进程的选择，并扩展[永久删除](../../implemented/feature/2026-11-07-native-session-deletion.md)的已打开聊天范围。原有父子关系、操作账本、未知结果不重放和任务核验规则继续有效。[VS Code 共享 owner](../../implemented/bug-fix/2026-11-03-vscode-shared-owner.md)处理另一条接入路径，不能据此认定 Desktop stdio 已共享。这三篇保留并互链；其他命中的 CLI、WSL 和归档笔记不由本提案替代。

## 提案

通过原 App 支持的 CLI 路径配置接入透明 stdio 适配器。适配器保留原 App 发出的初始化、配置、请求标识、通知和服务端审批请求；由同一个原生 app-server 提供同用户私有本机连接，Bridge 使用独立客户端身份执行操作。聊天执行、登录、权限和前台归属仍由原 App 维护，不修改 App 安装包或直接写入原生数据库。

首次切换只在显式初始化并即时核验空闲后正常退出、重开原 App。Bridge 断开或网关更新不能结束原 App 的运行时。原 App 的普通 CLI 工具、启动配置探测、计算机操作辅助运行时和 WSL 调用不得误接入这一共享服务。

生产接入尚未实现，也未切换当前主 App。完成原 App 的创建、删除和界面同步验收后，再接入既有创建与删除业务流程。

## 隔离证据与未通过项

使用 macOS 原 App 26.1103.41825、内置 CLI 0.167.0-alpha.3.2、独立 CODEX_HOME 和独立 Electron 资料。合成父聊天仅向 127.0.0.1 固定回显服务请求一次；未复制真实账号、未调用真实模型。

- 两个原生客户端共享同一运行时，可以在另一个客户端保持持有时创建 attached 子聊天与删除。
- 真实原 App 使用透明 stdio 后仍建立原生 Desktop IPC；Bridge 能发现其真实 owner。用户确认 App 能看到两个由 Bridge 创建的持久侧边聊天，并打开指定子聊天。
- Bridge 在确认父、子空闲且子聊天由原 App 持有后，原生 `thread/delete` 返回成功；原生 `thread/list` 已查不到目标。App 自己的连接收到 `thread/deleted`，随后收到使用 Bridge 真实注册身份发出的精确 `query-cache-invalidate`，并重查 attached 列表。
- **删除的双端界面同步未通过。** 用户截图确认侧边列表和打开标签仍残留，内容持续加载。原 App 的菜单将服务端列表与打开标签做并集；原生删除通知清理会话缓存，却未执行本地删除按钮回调中的关闭标签动作。因此只刷新查询不能解决此问题，不能把底层删除成功称为完整功能验收成功。
- 本轮隔离 App 已正常退出，后端退出码为 0；主 App 保持运行。核对无测试进程残留后，测试资料和下载缓存已清理，仅保留忽略目录中的脚本与证据。启动配置一次性调用透传已核验；辅助运行时分流、生产生命周期及 Windows/Linux 仍未验收。

## 备选方案

独立元数据运行时已有完整的写入账本与短生命周期，改动小；但不能跨越原 App 的写入者锁，因此仅适用于未被持有的原历史。

全局 `CODEX_APP_SERVER_WS_URL` 可以直接连接共享运行时，但当前原 App 在此模式下禁用本机客户端协调，包括 Desktop IPC 和部分状态广播，不满足保留现有接入能力的要求。

只发送真实身份的查询失效广播不会伪造 owner，且已实证可刷新新增列表；但删除时打开标签会把记录重新并入菜单，不能完成关闭标签同步。

伪造原生删除、归档或 owner 状态、修改 App 前端、直接删原生文件、在未知回执后重发删除均不采用。只读核对原生归档实现发现，它同样依赖菜单成功回调关闭标签；真实 `thread-archived` 广播不会调用侧边标签控制器。因此先归档再删除也不能完成同步，并会增加失败时留下归档中间状态的风险，不采用。

## 验收标准

- 原 App 持有父聊天时，Bridge 原生创建子聊天；两端保持相同 ID、父子关系和配置，原 App 无需重启即可查看。
- 原 App 打开空闲子聊天时，Bridge 经二次确认删除；原生记录、两端目录、打开的侧边标签均同步，不遗留加载中的空页。
- 未知写入不自动重放；任务、后代范围、账号配置与进程身份检查仍有效。
- 辅助 CLI 与启动探测保持原路径；Bridge 断开、网关正常退出与更新不结束原 App；原 App 正常退出能清理所属运行时。
- 分别验证目标平台后才开放相应能力，不把 macOS 隔离实验等同于三端成品。

## 风险

当前 App 没有已验证的外部关闭侧边标签协议，完整验收仍受阻。透明适配器会改变原 App 的子进程拓扑，必须核对原始启动参数、运行时退出、安装路径变化及多配置边界。普通方式再次启动 App 是否沿用初始化也尚未解决；不通过悄悄安装后台服务或改写系统环境处理。上述问题解决前不更新用户主 App 的启动方式，不将本提案标记为 implemented。
