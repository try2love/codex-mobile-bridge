# Agent Note: Codex 双端初始化与接口增量兼容

Status: implemented

## 问题

Codex 进程运行和账号配置可用不能证明网关已接入该 App 的执行器。原应用管理按这两个条件显示“已连接”，未接入用户没有直接初始化入口。后续 App 只新增启动参数或协议字段时，旧启动参数白名单也会跳过适配器，导致底层接口没变却失去连接。

## 决策

桌面网关、远程应用管理和本机 Desktop 聊天的断线提示共用“初始化连接”。按钮在默认本机 Codex 已启用、安装与初始化能力可用且无在途初始化时出现；已连接时保留“重新初始化连接”作为手动兜底。CLI、WSL、SSH 与独立配置不使用默认 Desktop 初始化。确认后两端均调用 Accounts 的 `initializeDesktopRuntime`，远程通过已有 `/api/clients` 严格限定初始化字段，委托同一事务并仅返回客户端状态，兼容共享中继；账号页保留 `/api/accounts/desktop-runtime`。认证、CSRF 与免密初始化拒绝保持。取消无写入；每次显式操作携带 UUID；未知结果不自动重放，等待状态隐藏重复入口。

“已连接”使用当前网关握手后的原生通道。新版同时核验 hosted 记录、私有端点、原生进程归属和通道代次；旧 IPC 要求真实 Desktop 快照，VS Code/CLI 快照不能作为 Desktop 证明。列表展示不新发阻塞 RPC。账号是否就绪仍由原账号逻辑负责，不能代替传输证据。

初始化复用原有的进程、配置目录、排队/未知写入和实时任务检查，正常退出后自动启动并核验。任务未知时先报告，再提供明确的额外确认；已知运行任务仍阻止重启。不以“自动恢复”扩大强杀或消息重放权限。[macOS 普通启动登记](2026-11-22-codex-ordinary-launch.md)保持现有实现。

Windows 沿用已存在的 MSIX/执行别名与私有管道初始化，按钮将“关闭后再开启”收进同一自动事务。[Windows/Linux 普通启动接入](2026-11-22-codex-windows-linux-ordinary-launch.md)进一步补齐独立用户分派器、Explorer 环境登记及真实 Windows 隔离验收；未构建完整 Windows 安装器。

Linux 为已核验的解包 Electron 布局增加同一 stdio 接入：从当前用户 `/proc` 取得 boot ID、启动 ticks、真实镜像、UID 和父子关系；原 App 持有适配器及执行器，使用已有私有 Unix 控制端点。初始化、账号生命周期和启动互斥覆盖 Linux；不借用 macOS 身份读取器。AppImage 等未核验布局不暴露初始化能力。

Linux 普通菜单启动在 XDG 用户 applications 目录覆盖同 ID 的唯一 `.desktop` 文件，只为所选原 Exec 增加 CODEX_HOME 与 CODEX_CLI_PATH，保留原参数和 URL 字段码，不修改系统入口。若入口声明 DBusActivatable，用户覆盖项将其关闭，确保菜单实际执行准备后的 Exec。找不到唯一入口或用户入口已选其他程序时保留原文件，仍可使用网关初始化。分派脚本在网关文件已移除时透传原 CLI。直接执行 GUI 二进制或未经过该菜单入口的启动不保证自动共享。后续已在真实 GNOME 桌面连续两次验证 PATH 菜单启动及原生读取，见[平台验收](2026-11-22-codex-windows-linux-ordinary-launch.md)。

## 保持底层连接的兼容规则

不按 Codex App 版本选择路径。建立连接依赖原生 App/host 归属、主要 `initialize` 身份、同配置目录、可用传输和必要控制结构。新增全局或 app-server 启动开关保留原顺序和值并交给原生解析；辅助 proxy/daemon/帮助/生成器命令和明确其他 listen transport 透传原生。已知多参数开关仍核对完整参数，不能把残缺命令当成新功能。

新增状态字段、消息项和通知允许通过，未知通知仍送达 App；只读取既有字段完成既有操作。原生流版本增大且控制结构未变时继续可用；请求 ID、执行归属、审批和未知写入规则不放宽。控制关键结构真正变化时拒绝控制，保留历史和初始化入口。代码及测试中的 Bridge 记录版本与内部投影版本不是 App 版本白名单。

## 备选方案

仅在账号页增加按钮改动最小，但用户仍要离开失败聊天寻找入口，故让应用管理与断线提示共用原事务。使用进程或端点文件存在作为就绪更便宜，但已复现假连接。通过每次启动参数变动更新白名单最保守，却违背底层接口不变时继续接入的目标；现在只识别传输和已知辅助入口，保留其余参数并在原生初始化后核验。Windows 普通图标覆盖需要独立可透传分派器与环境继承验收，后续实现与取舍见[平台接入](2026-11-22-codex-windows-linux-ordinary-launch.md)。

## 验证

定向源码回归覆盖两端同一事务、取消无写入、真实连接状态、过期通道代次、重复初始化、Linux XDG 覆盖与原文件保全、同安装 utility host，以及新增启动开关/字段/消息项/通知后继续读取和发送。HTTP 回归保持认证、CSRF、免密拒绝和显式未知任务确认。

真实 Chromium 在 1280 px 和 390 px 分别执行远程 8 项与桌面网关 4 项初始化断言：未连接时出现、确认后一次请求、取消零请求、在途隐藏以及已连接时保留手动恢复。浏览器使用合成客户端，不调用用户的真实初始化事务。Docker 本机 Linux 隔离尝试停留在容器 Created，已清理本次容器，不能作为 Linux native 通过证据；未安装新的工具或镜像。

全量 Node 回归为 1770 项，1769 通过、1 项跳过。Python 定向回归覆盖上述初始化、账号 HTTP、原生宿主、旧连接、Linux 源码和资源边界，模块依赖未新增例外。

笔记格式检查通过 286 篇；全库链接检查报告已有 `2026-11-12-chat-media-playback.md` 第 7 行的“本机路径”示例链接不存在，已核对本轮修改前即存在，保留在本次改动范围外。

初次验收的 macOS arm64 Test 包从独立 r3 目录运行，8788 网关自动切换。真实签名 Codex 的隔离副本连续两次普通 GUI 启动后，分别约 5.1 秒、3.0 秒建立 stdio 连接并成功读取原生列表，零模型请求；当前用户 App、适配器和执行器的 PID 全部保持不变。当时 8788 的实际客户端状态为已连接且隐藏初始化；后续已按用户要求保留手动入口。三个目标聊天均在后台接通；列表读取约 51 ms，已接通的时间线读取约 6–16 ms。冷读仍先返回保存的历史，不能把该次 HTTP 读取耗时当成原生连接完成耗时。

本机证据位于 `.local/installations/20261122-cross-platform-initialize/`：`browser-remote.json`、`browser-gateway.json`、`final-gateway-switch.json`、`live-http-verification.json`、`packaged-gui-verification.json` 与 `source-provenance.json`。旧原生适配器仍使用原包，未覆盖运行中的冻结程序；正式 8787、测试配置和原生 owner 保持不变。

## 影响

用户可在失败位置发起一次初始化，由网关完成必要的正常重启与连接核验。Windows 原生初始化沿用既有能力，Linux 新路径限于明确布局；后续两平台普通启动隔离验收见互链记录，完整成品与旧 GUI 的实机覆盖仍单独报告。后续只增加功能且保持当前控制接口的更新由增量兼容规则覆盖；移除接口、改变身份或关键状态结构仍需重新适配。
