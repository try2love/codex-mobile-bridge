# Agent Note: Android 可选后台通知与通知跳转保留聊天状态

Status: implemented

## 问题

原 Android 通知接收随前台状态停止，离开 App 后不能持续收到任务消息。通知跳转也会重建当前聊天，重复读取列表、模型和 Skill；在旧版上运行同组 243 项定向用例，有 16 项涉及导航、状态保留和读取顺序的失败。用户希望先在本地评审并体验 PR #85，保留贡献者历史，通过后再纳入 main，远程推送另行授权。

## 决策

本地评审分支保留 heiqiu47（acsq47@outlook.com）的五个原始提交，PR 头为 `cd8380115920ab24311155ef13cc850c5ab03369`。后台通知由用户手动开启，默认关闭；前台服务显示常驻通知并提供暂停。接收器按已认证电脑串行读取、按电脑并行，持久化游标绑定令牌摘要。首次连接或事件流替换只建立基线，既有事件不重放；退出登录、移除电脑和暂停使旧请求失效。

网关提供最长 60 秒的只读长轮询，事件或策略变化唤醒等待，返回前再次验证认证。旧客户端仍可立即读取；外部桌面设置保留原有刷新时限。通知候选发现可以复用按文件身份失效的 SSH 元数据缓存，账号切换、关闭应用等操作继续实时核验。

通知进入当前聊天时复用 WebView、时间线、草稿和工作台；跨客户端通知只选择已启用的目标，不自动启用客户端。打开聊天先读时间线，模型和 Skill 随后加载，过期账号或聊天的延后任务丢弃。已渲染的可见聊天通知原生端清理相应系统卡片，沿用 token、原始地址、当前 WebView 与前台校验。

Android 原生设置采用 PR 的独立全屏窗口，主题仅作用于设置页，后台开关和权限区域联动。Web/桌面样式与 HTML 不变；不能将设置页重做描述为“所有 UI 不变”。iOS 仅同步共享脚本注入所需参数，不增加后台通知能力。Test 使用原有独立安装和签名，实操反馈前不推进 main。

原设置页局部主题的范围由[安卓 App 统一主题](../bug-fix/2026-10-28-android-app-theme.md)部分取代；本篇保留原采用范围及通知、权限、导航决定。

Android 系统通知的会话级覆盖与查看后清理由[按事件独立保留](../bug-fix/2026-11-08-independent-mobile-notification-events.md)部分取代；不同事件保留各自卡片，后台服务与权限决定继续适用。

### 既有记录核对

- [网关 Cookie 隔离](../../implemented/bug-fix/2026-10-13-gateway-cookie-namespace.md)互补：继续按连接地址选择 Cookie，检查点绑定令牌，不改变旧认证决定。
- [第三方通知设置](2026-10-13-third-party-notification-settings.md)互补：Bark、ntfy、PushPlus 与本机权限独立，后台接收不替换这些通道。
- [回归与依赖门禁](../testing/2026-10-28-regression-and-dependency-gates.md)继续适用，构建和合成测试不等于真机后台可靠性。检索其余通知相关笔记未发现被本轮取代的决定。

手机入箱与第三方发送隔离、多客户端通知补漏及耗时记录见[通知投递隔离](../bug-fix/2026-10-28-notification-delivery-isolation.md)，保留本篇的后台开关、权限和导航决定。

## 备选方案

保留原前台轮询可避免服务常驻和额外耗电，但无法满足离开 App 后接收任务通知的需求。本轮选择默认关闭、明确开启与可暂停的服务，保留用户控制。

只用 FCM 或厂商系统推送更符合移动系统省电调度，但依赖额外推送基础设施和设备支持；现有可选 FCM 保留，本轮用自有网关的认证长轮询覆盖普通 APK。长轮询也不保证绕过 Doze 或厂商后台限制，需要真机继续验收。

每次通知重建页面能简化路由，但旧版复现表明它会丢失当前界面状态并增加前置读取。本轮只在同一已保存地址、相同认证及有效聊天页面复用，否则沿用完整连接流程。

## 影响

后台任务提醒和通知返回聊天具有可测试的恢复路径，代价是前台服务、持久化检查点和长轮询的维护及资源消耗。新设置页是明确的 UI 变化，用户实操验收尚未完成。未测量真实手机长时耗电、厂商省电策略或锁屏网络送达率，不据模拟器结果宣称这些问题已经解决。

## 验证

2026-10-28：基线为本地 `065b3c8`。同组定向 Node 从 227 通过、16 失败变为 243 全通过；全量 Node 1236 通过、1 项 Windows 专项跳过；Chrome/WebKit 宽窄视口 60 项通过；Python 通知、HTTP、SSH 发现、资源与模块边界 141 项执行，其中 139 通过、2 项平台跳过。

Java 接收器真实回环 HTTP/JSON 检查通过，覆盖流重置、游标、去重、并行电脑、暂停、断网恢复与登录/移除竞态；Android 权限、Cookie 续期、Android/Swift URL 检查通过。Android APK 编译和签名验证、iOS 无签名编译与资源检查通过。

独立空白 Android 35 模拟器中已核对设置页、默认关闭、开启后的实际前台服务、锁屏后本机测试通知和暂停后的服务降级；这些使用合成环境，不接入用户真实账号。详细日志和截图位于本地 `.tmp/pr85-20261028/`，不提交。作者此前报告的 Android 真机体验与本轮证据分开，未重新执行 iPhone 或 Windows/Linux 实机测试。

同日用户反馈：红米 K70、Android 16 在亮屏时可收通知、熄屏收不到，已保留 App 后台；对照使用 Google Play 版 ntfy 与 ntfy.sh。当时未核实该手机的电池豁免状态、ntfy 是否开启即时送达，以及熄屏时服务、CPU 和网络的实际状态，不能仅据最初反馈认定具体原因。

针对本地 `ff99198` APK 的补充复现使用隔离 Android 35 模拟器和合成 HTTP 网关，在亮屏、普通熄屏、两轮强制深度 Doze 后分别产生新事件。共 6 条事件均进入真实接收器并生成系统通知；第二轮连续产生 3 条事件，确认后续新长轮询也成功。系统记录为 `mWakefulness=Asleep`、`mState=IDLE`，服务保持前台；该镜像的 UID 网络策略为 `allowed=FOREGROUND`、`effective=NONE`。因此模拟器未复现用户问题，不能将通用 Doze 文档当作本机网络已受阻的证据，也不能将本次模拟器结果外推为红米熄屏验收通过。日志与夹具位于 `.tmp/android-doze-20261028/`。

随后用户将该手机的省电策略改为“无限制”，并在保持 Bridge 后台通知开启、熄屏后从电脑发起新任务的复测中明确反馈“已能在熄屏时收到”。本次真机结果由用户确认，支持该配置调整解决当前熄屏送达问题；没有修改产品代码，也不增加常驻唤醒锁。未取得真机运行日志，不能进一步区分此前是 CPU 挂起、网络限制还是服务调度；本次成功不替代整夜待机耗电、重启恢复或其他厂商设备的验证。
