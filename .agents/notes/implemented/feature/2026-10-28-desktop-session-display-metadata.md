# Agent Note: Claude 与 DSH 的显示分类及改名回执

Status: implemented

后续决定：[原生会话重命名](2026-11-04-native-session-renames.md) 根据用户新要求替代本文的改名别名回退。本篇保留当时的选择与理由，Bridge 项目/分区分类仍沿用。

## 问题

[共享会话菜单](2026-10-28-shared-session-menu.md)初次整合时，仅向具有原生分类 API 的 Codex 提供项目和分区。用户随后明确要求 Claude、DSH 也具备这些整理入口，并接受在没有可验证原生接口时使用明确标注的 Bridge 分类。不同客户端的项目语义不能通过改 cwd 或重新创建聊天来强行统一。

## 决策

网关持久化 `DisplayMetadata`，记录 Bridge 项目、分区及显示别名。界面在相应操作页显示“仅在 Bridge 中生效”；手机与 Web 读取同一网关记录。分类按 provider、接入目录、原生 home、host 与 backend 隔离，避免 Code、Cowork、CLI、WSL 或其他 DSH 实例互相套用标签。原有会话 ID、cwd、owner、provider、auth 不变。

具有可验证原生能力时优先使用原生操作：Claude Code/Cowork 原生改名；DSH 已加载会话原生改名和同 cwd 的工作区成员变更。Claude CLI 及未加载的 DSH 会话使用显示别名，不为改名启动会话。DSH 的分区仍是 Bridge 分类；项目与分区分别标明作用范围。原生具体接口、冷会话限制及版本核验由[原生接入笔记](2026-10-28-native-session-metadata.md)记录。

`RenameCommands` 在原生写入前保存目标标题和执行身份；结果未知后，新请求 ID 或网关重启均不能重复派发。后续只读查询确认原目标后才解除阻塞。明确 `notSent` 的操作可以修正重试。原生改名确认后清除旧 Bridge 别名，使列表和聊天标题显示原生结果。原生项目继续复用 `OrganizationCommands` 的预期成员关系和持久化未知结果保护。

Bridge 分类创建与选择、显示改名在同一私有原子文件事务中记录请求回执；同一请求重试不会创建重复分类，也不会把后来的分类改回去。项目选择使用预期成员关系，拒绝过期页面覆盖其他客户端刚完成的选择。列表按项目显示时使用显式分类及分区，未设置显示分类的旧会话继续保留既有目录展示方式。

## 验证

`tests/test_display_metadata.py` 覆盖跨进程对象重建后的持久化读取、分类/别名隔离、原身份不变、重复创建回执、过期选择拒绝、原生未知改名不重放、明确未发送可纠正、原生改名清理别名及 DSH 原生项目与 Bridge 分区混合范围。浏览器从已登录合成列表进入三家菜单，验证改名、项目、分区与返回，不操作真实会话。构建与共同回归证据保存于 `.tmp/session-followups-20261028/`；合成原生接口测试不等于所有第三方客户端实机验证。

## 备选方案

继续隐藏缺少原生接口的入口最容易保证原生一致性，但不能满足用户明确提出的跨客户端整理需求。把 Bridge 分类冒充原生项目会误导用户，也可能诱导通过改 cwd 迁移执行环境，因此采用分项作用范围提示。直接调用 DSH `sessionController.rename` 虽然接口简单，却可能恢复冷会话；因此保留非激活的原生能力边界及显示别名。

## 影响

新增网关私有 `display-metadata.json`、`session-renames.json`，不会修改原生历史文件。Bridge 显示分类不会同步到原客户端；不同网关数据目录也不共享这些记录。会话未知写入需要原生读回核对，不能通过重复点击绕过。当前分支只在本地，不推送或发布。
