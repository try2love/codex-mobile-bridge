# Agent Note: 桌面以扫码确认替代手工比对安全码

Status: implemented

## Problem

同账号出现多条同名手机，手工比较八组安全码才能识别待授权对象。关闭旧绑定和重新批准分离时，失败易留下两条状态不清的授权。

## Decision

当前电脑只展示已收到 Noise 身份证明的待确认请求。二维码在本机生成，包含绑定 ID、完整安全指纹和随机挑战；手机核对指纹后，通过同一 Noise 身份回送挑战。挑战有时限，不发给云端。扫码并不授予权限；只有桌面明确确认才保存可信 pin 并提交授权。

同安装修复携带确定的旧绑定；换机时，桌面可按短指纹区分旧条目，选定一条后「允许并替换」。服务器确认撤销后，桌面移除该旧 pin 并关闭其本地及 P2P 通道。原开关仍只暂停或恢复已批准的绑定。未知写入不自动重放。撤销历史留在服务端，不混入可授权列表。

不配新手机时也可[单独删除旧云设备授权](2026-11-20-desktop-cloud-device-delete.md)，不改变本篇的原子替换规则。

设备名称后的 8 位短码取完整安全码的最后一组，供手机云服务中心对照。桌面按当前语言显示在线和离线，使用服务端返回的手机在线状态。

## 记录归属

- [同账号目录](2026-11-03-account-device-auto-discovery.md)的自动建绑定改由显式请求；原可逆开关、关优先代次栅栏和权限独立规则保留。
- [桌面批准](2026-11-03-desktop-approved-cloud-pairing.md)的完整指纹与双端私钥证明保留；本篇只替换人工比对与无期限待确认。
- [当前云契约](../simplification/2026-11-04-prerelease-cloud-contract-cleanup.md)的旧请求接口仍退役；[网页云服务](2026-11-07-cloud-web-proxy.md)不参加手机配对。没有重复的新提案。

## Alternatives considered

- 保留安全码手工比对有利于没有摄像头的用户，但识别成本仍高。复制同一个二维码载荷可在无摄像头时复用同一安全校验。
- 同账号自动授权无需人操作，但登录不是电脑对手机的信任。保留一次本机确认和完整加密证明。

## Testing

Python 云套件覆盖挑战错误与身份变化、未扫码批准拒绝、原通道和关闭语义；Node 界面覆盖扫码前无批准、确认只提交选定旧 ID、迟到目录与离线停用。

浏览器合成目录用 `trusted: true` 与 `active/disabled` 表示已有授权；未验证的待配对请求不显示，证明已验证但尚未扫码时不提供批准，扫码核验后点击批准才提交一次带 `confirm_pairing` 的写入。夹具先读取目录并确认已信任开关，再开始记录业务操作，初始化读取不混入赞助或语言切换的调用次数。[v2.2.2-preview.3 同步](../simplification/2026-11-16-cloud-only-fork-scope.md)的云面板 184 项浏览器检查通过，覆盖 Chromium/WebKit 宽窄屏；这些合成结果不扩展为手机扫码或真实授权验收。

2026-11-20 云专项的 124 项 Python 和 44 项 Node 测试通过。本机 arm64 Local 包使用原本地签名身份。覆盖安装后核对了应用、网关和桌面资源，账号、绑定、身份凭据记录和会话文件的摘要一致。本机网关健康并连上已升级的官方云。实体手机扫码和聊天读写仍待真机验收。

同日的在线文案修复通过 45 项 Node 云专项，包括在线和离线在中英界面下都使用同一语言。Local 包已覆盖安装，原账号和配对文件摘要一致，网关重新连到官方云。

## Consequences

电脑列表区分当前请求和现有授权，不需抄写长指纹。首次仍需手机在线、可扫码或粘贴，并要求服务端与手机支持新版本。恢复已批准连接不需要重新扫码。
