# Agent Note: 网关作为 ZCode 官方远控终端的独立实验

Status: implemented

## 问题

私有管道需要由网关启动原 App。对于用户已普通启动的 ZCode，期望不重启、不打开调试端口，也能接到同一个任务执行者。用户允许在独立本地分支验证官方账号远控，由网关承担终端身份，手机只登录 Bridge。

## 决策

实验分支 `experiment/zcode-official-remote-20261104` 基于 v2.2.0-preview.2 的 `78014a9`，保留默认私有管道。独立只读探针保留在 `scripts/zcode-official-remote/probe.mjs`。Mac Test 在 ZCode 独立管理页增加可选官方远控，默认仍使用本机连接。网关专用官方登录窗口取得自己的终端凭据，用 Electron safeStorage 加密后保存于当前 Test 数据目录；不复制原 App 凭据，不通过远程网页下发 JWT。探针的 JWT 仍只从标准输入进入内存。设备列表必须确认二维码的 SID 与 MID 同时属于当前账号，且 MID 与当前配置目录的 `telemetry-state.json` 中本机设备一致；不自动选择其他在线设备。

协议依据 ZCode 官方源码 `a9fe401eede6e6e5e01be9048679c206fe6f02d9` 的 Relay V2。只请求 terminal 一次性票据，核对 auth_ack，再发 bootstrap 和工作区列表。Test 连接一个已返回的本机工作区容器，不传 taskId、不自动接续某条聊天。复用官方 RPC、ACK 分片和 SessionDataLayer，以 `web-remote-replayable` 握手；现有本机路径仍严格校验 `desktop-continuous`。官方源码固定到构建输入并附许可证，不强制原 App 安装相同版本。每次显式重连取得新票据；KICKED、认证失败和断线终结旧 RPC，不自动争抢终端或重放写入。

官方页面、设备和会话数据会经过智谱中继。这是用户本次明确接受的可选实验，不改变本机接入默认边界。

后续[统一连接选择与 API 配置](2026-11-04-zcode-connection-choice-and-api.md)补齐桌面与手机的方式选择、链接独立保存和旧登录迁移，并移除生产管理页的 TCP 兼容入口；本文的官方传输、身份校验与未知写入边界继续适用。


Electron 主进程持有官方终端，Python 适配器通过当前数据目录登记的私有 Unix socket 调用；不新增 TCP 监听。记录文件为 0600，socket 父目录为 0700，请求需随机令牌，回执过滤内部异常。关闭网关窗口仍由现有托盘保留主进程；退出网关桌面进程会断开官方终端，原 App 继续运行。此实验只开放 Mac 管理入口。

`ZCodeOfficial` 继承原适配器的消息、附件、审批、历史和回执处理；共享 renderer 接受可信运行环境，普通请求不能指定或替换环境。连接身份由 relay epoch 与 device 组成，发送前两端核对，旧身份不能跨重连复用。未知回执沿用原有防重放策略。被动列表和状态查询不建连接、不接管聊天；显式重连和用户进入聊天才恢复会话租约。

## 备选方案

私有管道不依赖官方网络，且现有操作已适配，因此保留为默认实现；但不能附着到任意已普通启动的进程。TCP 兼容端口能复用既有协议，同样需要启动参数并增加本机访问面。官方远控复用原执行者，但引入官方账号、远程服务可用性及单终端互踢约束；只有验证真实登录和同一个原生工作区后才能继续产品化。复制现有消息/附件/审批代码可快速实现一个独立官方客户端，但会造成两套行为长期分叉，因此选用可信环境注入和共享适配器。

## 测试

`node --test tests/zcode-official-remote.test.mjs` 的 14 项模拟测试通过，覆盖错误账号/设备、SID 回包不符、错误请求 ID、认证过期、KICKED、超时与清理、一次性票据不复用以及诊断不包含凭据。模块边界检查通过，生产入口不导入探针。

2026-11-04 的 Mac 原 App 3.17.2 实验使用官方网页登录，由用户完成同账号认证。Mac 的登录渠道为 Z.AI；误选 BigModel 时，即使手机号相同也返回账号不匹配。只核对原 App 凭据元数据中的渠道及官方页面账号身份，没有解密或复制原 App 登录凭据。验证原型必须先区分 provider，再比较账号，不能把手机号或显示名相同视为同账号。

独立 Node 终端通过官方 HTTP/WS 服务取得设备列表与新票据，完成配对、bootstrap、工作区列表和指定原测试项目的 `workspace-bridge-ready`。首次累计耗时分别为 129 / 208 / 357 / 434 / 510 / 591 ms；确认终端关闭后重新接入分别为 97 / 162 / 278 / 343 / 410 / 476 ms。两次均只有一个原生工作区，模型请求数为零。这是同一次网络环境的两次样本，不代表弱网或长期性能。

官方网页也展示了同一原 App 的任务列表。该网页自己的 RPC 实现不能算作探针具备聊天收发能力。实验没有重启 ZCode、开启 TCP 调试端口或替换现有 Test；原 App 已启用官方远控，因此尚未证明普通启动后可以由网关自动启用它。

实验结束关闭专用浏览器终端，并通过原 App 的“停止”操作撤销本次启用的官方远控；原 App 明确显示“已关闭 Web 远程控制”。原 App 和既有网关不退出、不切换账号。

新增适配器 8 项测试、管理路由 2 项测试、官方协议与共享数据层 3 项测试、主进程凭据/本机身份/私有 IPC 5 项测试通过。协议测试使用官方 ChannelServer/ChannelClient 和 ACK 实现，覆盖 1.4 MB 分片、连接中断、KICKED、旧 owner、错误设备与待确认写入不重发。管理页套件通过，刷新状态不新增轮询。

Mac Test `2.2.0-preview.test.128.8` 构建与签名通过，冻结 PYZ 包含官方适配器和本机 RPC，归档中的 renderer 与源码一致。独立 8790 数据目录中，全部 Agent 关闭，验证官方私有 IPC、未登录状态、适配器选择、HTTP health 与静态资源；正常退出后 IPC 登记清除。未读取模型账号、未发模型请求，真实 8788 的登录和原会话连接不计入这次独立烟测。

8788 成品初次登录时，Z.AI 手机号页面出现“手机号格式不合法”，实际 `/api/v1/auths/phone/send-code` 返回 HTTP 422、`{"detail":"The captcha verification failed."}`。请求没有 `captcha_verify_param`，不是手机号输入缺少数字。官方前端 `prod-fe-1.1.126` 的 `_page-CN9LF7aI.js` 将所有 422 映射为手机号格式错误；验证码初始化失败时还会尝试不带验证结果的短信请求。这是错误提示误导，不能据此修改手机号、跳过验证或判定账号无效。

同一窗口的阿里云 `InitCaptchaV3` 请求在官方设定的 10 秒后取消，主备验证地址均出现超时。无账号的 GET 与空 POST 连通性对照能在约 0.1–0.5 秒返回，因此仅能确认具体验证码初始化请求失败，尚不能区分上游验证服务、代理路径或内嵌浏览器兼容性。普通浏览器对照因控制工具超时没有得到可比结果。没有放宽登录窗口安全边界、修改全局代理或改写第三方验证脚本；用户随后手动完成同一个 Test 的登录和官方连接，该次初始化异常的更底层原因仍未确认。

用户登录后，成品私有状态接口确认 Z.AI 原账号、官方连接与配置选中状态一致。手机同用的局域网 HTTP 接口读到 6 条原生会话和 1 个项目；只接续已有的独立验收 Fork，恢复 18 条历史消息、发送权限以及附件/模型/Skill/权限等能力，模型保持 GLM-5.3-Flash、low。只断开并重连官方终端，未退出原 App；重新连接耗时 2173 ms，owner epoch 更新，原 Fork 接续后仍可写。局域网详情读取 577 ms；固定 HTTPS 经过真实网关登录后读取相同会话为 2261 ms。以上为本次样本，不代表弱网或长期性能；没有发送模型消息，因此不能计作真实模型收发、停止或审批验证。

`/api/health` 的公网 403 正文为“仅允许本机状态检查”，属于接口边界；Test 关闭回环网页访问时，回环 `/api/login` 也按配置拒绝。验收改用已启用的局域网地址与固定 HTTPS 的 `/api/auth`、登录和会话接口，没有改变这些访问限制。

## 影响

结果证明网关侧独立终端可以用官方账号接到原 App 的工作区，手机不必持有智谱账号凭据。Mac Test 已接入管理页、官方登录安全存储和共享聊天 RPC，并验证成品会话接续、读取与官方终端重连；可写能力返回与协议模拟通过不能替代真实收发。普通冷启动、锁屏恢复、发送、停止、审批与附件仍需真实验收，本次不发送真实模型消息。Windows/Linux 官方方案尚未构建。

新 terminal 可能替换同设备的官方手机网页，不能自动重连争抢。官方服务可能与已公开源码版本不同；必须校验实际响应。认证失效需要用户重新登录；官方原 App 的首次远控启用和重启后的自动恢复不能由一次配对成功推定。
