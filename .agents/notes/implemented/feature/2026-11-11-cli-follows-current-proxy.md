# Agent Note: 本机主 CLI 跟随已核验的代理端口

Status: implemented

## 问题

CLI 服务仍继承旧的回环代理时，用户换端口后必须手动恢复。直接采用网关启动环境可能使用另一个配置或旧终端的代理；自动启用全 home 的原生系统代理还可能改变绕过规则。

## 决策

只在本机主入口同一 CODEX_HOME 的 CLI 会话被明确继续或提交新操作时检查。APP、IDE、独立入口、SSH、WSL 和只读历史或通知不采用主入口的代理。原生已配置 `respect_system_proxy` 时交给原生选路，不因旧继承变量排空进程。

读取原生已核验代次的代理和绕过变量。只有当前模型目标不会直连或绕过，原代的相应回环代理已不可达，且当前用户的系统设置给出另一个可达的同协议静态回环地址，才安排恢复。macOS 使用一次 SystemConfiguration 快照；Windows 读取[原生 resolver 使用的当前用户 Internet Settings](https://github.com/openai/codex/blob/c40729ea5cf8e947481b130c59807273eda2f8e9/codex-rs/http-client/src/outbound_proxy/windows.rs#L54-L90)，不用全局 WinHTTP 代理或网关继承变量。PAC/WPAD、大小写冲突、无法判断的绕过规则或没有可信替代时不猜。Linux 本次未验证出可通用读取的可信系统替代来源。

复用[同 home 待闲事务](2026-11-11-cli-recovery-waits-for-idle.md)，保持原 ID、cwd、provider 和已有原生权限。只替换受影响协议的继承变量，保留其它协议、NO_PROXY 和未经授权变更的认证；同时发生已核验的账号变更时走同一次维护。等待中代理目标变化使旧确认失效；派发前再核对旧地址仍失效、新地址仍可用，原代已正常退出后采用当前重新核验的有效地址，确认新代实际继承该代理后才接续。没有写系统代理或 native config，也不重发已发送、结果未知或这次被拦下的草稿。

## 备选方案

保留旧的手动恢复：其配置写入需要明确确认、原生配置版本比较和未知回执处理。自动路径不偷偷写 `respect_system_proxy`；上游在使用系统代理路由时并不沿用环境中的 NO_PROXY。设置已生效的会话继续由原生动态处理，新启用系统策略也不能热更新任意已加载的模型客户端。直接使用网关启动的代理环境不能证明当前地址有效或属于此配置。

## 验证

回归覆盖原生动态策略、同协议选择、不同 home、绕过/PAC/变量冲突、旧地址仍有效或新地址不可达、并行认证变化、等待期间代理变化，以及替代进程未采用预期代理时不接续、不二次退出。

真实 macOS CLI 0.167.0 在独立临时 home 用自有 TLS 响应与回环 CONNECT 代理验证。旧 A 收到原线程和另一活跃线程的两个请求；关闭 A 后新草稿未入账，等待活跃任务完成后正常重建。同一线程和 cwd 冷接续，之后明确送出的新消息才实际经 B 完成。三次预期 POST 都到合成端点，原消息没有重放，HTTP/ALL/NO_PROXY 及配置字节不变，两代隔离进程都退出。OS 查询结果是夹具注入，没有改全机设置；Windows 的系统源行为在本次是协议和模拟回归，未以此声称实际代理切换。证据为 `.tmp/feedback-20261111-10/cli-auto-proxy-native-result.json`，首轮测试证书失败及自有进程清理另存。

## 影响

已能核验的本机坏代理端口可在明确的新 CLI 操作触发后安全恢复，原草稿由用户重新发送。没有替代证据或未知恢复回执时保留原有诊断与人工检查；不会借用其他配置的代理，不新增强制退出能力。
