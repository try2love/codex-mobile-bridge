# Agent Note: 网关协助 Android 查询和下载安装包

Status: implemented

## 问题

手机无法访问 GitHub 时，应用内检查版本或下载 APK 都可能失败；浏览器入口不保证改变网络可达性。电脑网关可能有可用网络，手机也已建立对该电脑的认证连接。

## 决策

Android 查询版本保留直接访问 GitHub、失败后通过当前已连接电脑重试的路径。初版下载也采用此顺序，理由是 API 不通不代表 APK 下载地址不通；这一下载自动回退决定已由 [下载方式选择记录](2026-10-12-android-update-download-choice.md) 部分取代，查询备用路径和下面的网关契约继续适用。手机选中的版本、大小、摘要必须与网关从固定官方仓库读取的资产记录相同；网关只接受版本与资产身份，不接受任意 URL。安装交接继续使用 [Android 更新交接记录](../bug-fix/2026-10-12-android-update-handoff.md) 的已完成文件恢复机制。

网关先完整下载到私有缓存并校验，再通过已认证下载接口传给手机。准备请求使用 CSRF，进度查询不占用长请求。下载缓存只保留于当前运行周期，闲置超过 24 小时按需清理，最多两个任务/缓存，每次一个后台下载，每包最多 512 MiB。手机取消等待保留电脑后台任务，其他已登录手机可复用；手机端没有跨进程保留未完成下载的承诺。

现有附件传输的范围协商和中继流式协议继续复用。中继、连接器和网关都限制准确的更新路径与方法，网关认证信息只发往选定地址，GitHub 请求不携带这些信息。手机再次核对完整 APK 的大小和摘要，最终交给系统安装器确认。SHA-256 用于检测损坏，不被描述为独立的发布者签名。

## 备选方案

- **只保留手机直连和浏览器兜底**：单端实现、维护简单，但手机网络完全不可达时，两条路径都可能失败，不能利用已连接电脑的网络。
- **只代理 APK 文件**：新增接口较少，但手机可能无法获取版本信息，根本到不了下载阶段，因此查询也需要网关备用路径。
- **电脑边下载边直接转发一个长响应**：可以减少首次传输等待，但下载和手机断线耦合，重试与长时间无数据返回的处理更复杂。先缓存使完整性、进度和重试边界明确。

## 测试

`tests/test_mobile_updates.py` 覆盖发布通道、固定来源、资产身份、并发复用、失败重试、完整校验、过期、认证、CSRF 和范围响应；`tests/test_shared_relay.py` 通过真实本机连接器验证新接口。`GatewayUpdateDownloadTests.java` 验证带设备前缀的认证下载、摘要、禁止重定向和缓存失效后的重新准备。构建与模拟器证据保存在忽略提交的 `.tmp/pr32-gateway/`。

独立测试包使用局域网固定夹具模拟手机查询和下载均失败、仅下载失败；两种场景均经打包后的 macOS 网关完成 Android 模拟器内安装。安装权限页面期间终止 App 后台进程后可恢复安装；同版本测试更新可再次触发并完成。最终从模拟器取出的已安装 APK 摘要与提供的目标包一致。这些模拟结果不代表真实 GitHub 网络已验证；用户随后报告实测通过，并授权仅合并源码。

## 影响

手机可以利用电脑的网络完成更新，电脑也可以复用已下载包。代价是网关存储、传输流量和跨端协议维护；共享中继当前遵循[统一 HTTP 业务权限](../architecture/2026-11-10-http-forwarding-without-route-policy.md)，无需新增接口名单。电脑同样无法访问 GitHub 且没有缓存时，功能不能解决网络问题。旧网关不影响手机原有直连路径。

历史检索只命中前述安装交接记录，属于部分重叠：原先 GitHub 下载及安装恢复约束继续适用，本篇增加经网关传输的来源类型与认证契约，无其他提案需要归档。
