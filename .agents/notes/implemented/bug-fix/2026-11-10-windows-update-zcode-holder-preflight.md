# Agent Note: Windows 更新在下载前检查仍占用安装的 ZCode 持有进程

Status: implemented

## 问题

ZCode 私有管道持有进程在网关或管理窗口退出后继续等待原 App 退出，以免断管中断原任务。Windows 上该进程仍运行安装目录内的冻结网关 EXE 和 DLL；更新无法把整个安装目录移动为备份。

原生隔离夹具从临时目录运行同一冻结网关，仅等待 stdin，不操作真实任务。工作目录在安装目录外时，移动安装目录失败为 `WinError 5`；工作目录在安装目录内时失败为 `WinError 32`。两个夹具正常关闭 stdin 并以退出码 0 结束后，移动立即成功。只迁移 cwd 因而不足以修复此问题。已有目录移动重试能等待短暂清理，临时 cwd 锁在 2.625 秒后释放时已验证成功，但不能解决持续运行的私有持有进程。

历史 Windows 日志中的一次 Tailscale 启动门禁失败与一次目录移动 `WinError 32` 分别保留；后者在约 145 秒后的尝试成功。旧失败计划与占用者身份已缺失，不能断言历史失败一定由 ZCode 持有进程引起。

## 决策

Windows 更新点击进入包下载前，通过现有私有桌面 worker 执行只读预检。预检只匹配目标安装的实际网关 EXE，在同用户、同桌面会话重新核验进程身份、出生时间及精确 `zcode-pipe-host --data-dir … --application …` 角色。明确仍运行的持有进程阻止下载，提示用户先结束任务并正常退出 ZCode 后再更新。没有进程、已经退出的 PID、其他安装和实际无关的 worker 不阻止更新；无法取得角色或进程世代变化时拒绝本次预检，不把不确定性当作安全。

准备阶段在读取归档与创建事务前重新检查；应用阶段在父进程退出后及移动安装前再次检查，保留原有停止、版本、ACK、备份与回滚约束。预检不会正常退出或强制结束 App，不修改任务、账号、绑定，也不读取陈旧 holder 元数据决定是否放行。macOS 与 Linux 不增加此 Windows 门禁。

本记录补充 [POSIX 父进程退出核验](2026-11-10-desktop-update-parent-exit.md)和 [ZCode 私有管道生命周期](../architecture/2026-11-03-zcode-desktop-management.md)。Mac 的已发布签名 peer 迁移夹具只覆盖可重命名的 POSIX 安装，不作为 Windows 热迁移完成的证据。

## 备选方案

复制可长期运行的独立 holder 运行时可以支持更新时保持 ZCode，但同时要求新的发布物生命周期、旧版本保留策略和 peer 身份协议，不属于此次最小修复。仅修改 cwd 已被上述原生锁区分否定。强制结束 holder 会关闭原 App 的匿名管道，可能中断用户任务，因此禁止作为更新回退。仅在下载后拒绝能避免错误替换，但仍浪费首轮包下载，因而同时增加下载前检查。

## 影响

已证明不可完成的 Windows 替换在下载前给出可执行的恢复步骤。用户正常退出 ZCode 后可以沿用已签名候选重试更新。此改动是提前阻断，不是无损热迁移；原 App 任务和正式资料保持由用户控制。预检增加有界的本机进程查询，准备与替换前的复核用于缩小竞态窗口，不能替代文件系统替换与回滚保障。

旧版更新器由旧安装执行，新包里的预检不能反向修复旧版负责执行的首次升级；旧版需要用户在更新前正常退出 ZCode。此次不执行真实 App 更新。

## 验证

Node 回归先证实原实现仍继续下载安装，再验证新预检拒绝时不下载包、不调用安装回调，解除阻塞后可重试。Python 回归覆盖实际持有进程、无持有进程、已退出 PID、其他安装、无关角色、不可读身份和 PID 世代变化，并覆盖准备前以及应用过程中出现新 holder 时保留原安装。相关执行 34 项 Python（其中 1 项平台跳过）、34 项 Node 与 4 项平台架构检查通过。

Windows 原生预检在同用户 Session 1 检查真实冻结 `zcode-pipe-host` 进程：无 holder 时放行；同安装实际 holder 存活时拒绝；检查另一安装时放行；holder 自身 45 秒闲置期限结束、退出码 0 后，即使隔离 profile 仍在也恢复放行。夹具没有发送初始化请求，没有启动或退出 ZCode，没有强制结束进程。该证据覆盖原生进程判断，下载前接线与事务竞态分别由上述源码回归验证；不声称已经执行真实应用更新。
