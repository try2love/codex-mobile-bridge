# Agent Note: SSH 离线隔离、退避与本机历史刷新

Status: implemented

## 问题

用户反馈 SSH 服务器离线后，局域网和固定 HTTPS 下的本机会话都无法重连；正式版 v2.1.6 与现有 Test 同时受影响。手机持续连接后提示“桌面仍在加载此聊天”，既不能取得最新内容，也不能发送。用户要求离线 SSH 不影响本机操作，自动重试采用退避，并在账号管理提供手动重试。

隔离复现确认三个 Bridge 缺陷：本机与 SSH Bridge 共用账号操作锁，远端激活读取等待会阻塞本机激活；连续五次离线读取会启动五次 SSH；本机 Desktop 会话失去实时连接后不刷新已有保存记录。对应测试均在修复前失败。旧聚合列表、活动和通知发现还会同步等待远端元数据，必须与本机读取分离。

初次现场另有独立的原生层问题：8787、8788 的健康接口均返回 200；独立的原生 IPC 初始化成功，但三个最近本机会话均未返回 owner，订阅也未收到状态快照。按当前安装版路由源码的十秒发现期限延长单次只读查询后，得到 `no-client-found`。这次检查不经过网关、不激活聊天、不发送消息。已安装版本仍支持原有 owner 协议版本和状态版本 11，不能据现象判断为版本升级不兼容，也不能据 Bridge 的缺陷推断它就是现场故障的唯一原因。

## 决策

普通原生操作按主机串行，不同主机可以独立推进。全局账号变更及应用启停继续使用排他门锁，只有所有主机的在途操作结束才可取得；门锁支持原有嵌套调用。根 Bridge 上的目录、信任及创建入口按实际目标主机进入对应操作门锁。离线主机不能被当作空闲证据，既有 owner/provider/auth/cwd、停止核验和未知写入保护保持有效。

Codex 关闭请求取得排他门锁前最多等待两秒。若连接或其他操作仍占用门锁，立即返回“有 Codex 操作正在进行，尚未执行关闭，请稍后重试”；不退出、不修改启用偏好、不后台排队，也不在原操作完成后自动重放关闭。用户显式重试成功取得门锁后，继续执行完整的新鲜任务核验与原生进程身份检查。这一上限只限制排队，不能用来缩短弱网下的任务核验、把超时当作空闲，或代替正常退出流程。

共享客户端生命周期只在阶段耗时达到两秒或阶段失败时记录 `operation-wait`、`task-check`、`native-stop` 的结果与耗时，正常快速操作不增加日志。日志不包含会话身份、正文、账号或凭据。门锁等待、任务核验和原生退出分别计时，不能把连接积压一概归因于操作系统退出慢。

`bridge/features/network/retry.py` 保存共用的主机退避规则及按 SSH 别名隔离的进程内状态。Codex 的元数据、目录、文件读取和 Claude Code 的只读 SSH 辅助请求复用同一状态，不为客户端各写一套重试算法。连接失败的等待从约三十秒开始翻倍，加入 0.8–1.2 的随机抖动，上限十分钟。等待依据单调时钟；界面单独换算预计重试时间。连接恢复后清零失败次数；并发旧请求的成功不能覆盖后来已确认的断连。远端业务脚本报错不计作 SSH 传输离线。

冷却期内读取快速失败，到期只允许一个恢复尝试。既有维护循环按退避期限发起只读连通性探测，不按固定间隔重复建立连接；已移除或别名已变化的登记主机不再自动探测。自动探测只运行固定的 Python JSON 回应，不保存或重放创建、发送、审批及其他写入。状态不持久化，网关重启后从未知状态重新建立证据。

账号管理使用现有共享 `AccountsPanel` 显示已登记 SSH 主机、当前探测状态、下次重试时间和“重试 SSH 连接”。手动操作跳过冷却期，同主机在途探测合并；只读探测在后台执行，HTTP 不等待 SSH 超时。网页入口保留登录、Host、Origin 与 CSRF 校验，只接受主机 ID，不接受客户端提供别名、命令或路径。桌面控制入口沿用同一服务方法。探测恢复只证明 SSH/Python 可用，不代表原生会话 owner、模型服务或任务已经恢复。

聚合列表、活动和通知发现使用有限的后台远端读取与短时缓存，本机结果不等待 SSH。单独指定远端主机的列表仍可等待该主机，以保留健康连接的首屏响应；未完成或失败的聚合读取沿用不可用主机反馈。被动读取仍不激活任务。

项目操作的锁路由只解析已登记主机与项目 key，不为选锁枚举全部主机。创建聊天仅枚举已选主机的项目，仍以完整 key、目录身份和原生项目记录验证目标；项目聚合列表的 SSH 历史使用既有 `RemoteStore.poll`，不等待离线读取。Windows 原生回归曾卡在项目信任入口，线程栈证明是选锁枚举项目后向无效 SSH 写入脚本，而不是信任接口自身的读写。

新建 CLI 聊天在用户选中 SSH 环境时只读取该主机的项目，补齐聚合后台读取尚未完成的历史项目。默认本机弹窗不等待 SSH；切回本机、关闭弹窗或换环境后忽略迟到结果，读取期间禁止提交旧选择。沿用同一项目服务、目录身份和鉴权，不增加定时轮询。回归覆盖首次远端项目、单主机请求、迟到结果与未登录拒绝。

Codex 和 Claude 的一次性 SSH 输入共用 `features/network/stdio.py`：将 UTF-8 输入写入独立、自动清理的临时文件，再把句柄交给子进程 stdin。Windows `communicate()` 会先同步写入 PIPE，再进入超时等待；当 SSH 不读大脚本时，原有 `timeout` 无法限制这次写入。文件句柄避免父进程等待管道容量，保留原超时、输出解码和退避分类。路径和内容不进入 argv 或日志；持续交互运行时的协议保持不变。

本机 Desktop 与 CLI 会话在断开实时连接时，共用原有两秒间隔的保存历史刷新；记录不变不推进时间线，已连接 owner 继续提供实时状态。历史刷新不能证明会话可写，发送仍必须取得原生执行连接。

## 备选方案

仅增加连接超时能容纳健康慢响应，但不能解除跨主机共享锁，也会延长离线等待，因此不作为修复。仅增大固定重试间隔改动更少，但无法兼顾短暂断线恢复与长期离线负载，因此采用有上限的指数退避和显式重试。

完全移除账号门锁可以避免等待，但会让账号替换或应用退出与在途原生写入竞争。因此保留全局排他操作，按主机隔离普通操作。 保留关闭请求无限排队可避免用户重试，却可能让手机超时后原生退出才执行；因此超出排队上限就明确拒绝。缩短全量任务核验、仅查当前聊天或把 owner 查询超时视为空闲会减少等待，但会遗漏其他原生任务，本轮均不采用。

单纯提高 Windows 子进程超时无法解决发生在超时检查前的同步写；新增发送线程与回收协议会增加线程生命周期复杂性。因此一次性输入使用已有文件句柄，代价是少量临时磁盘 I/O。实际不读取 stdin 的子进程加 1 MiB 输入用于验证超时，Unicode 回显用于验证字节保持，文件在成功和异常出口均自动关闭。

在原生 owner 不可用时另起 app-server 接管 Desktop 聊天可以绕过当前失败，却可能改变执行归属并与原生 writer 竞争。本次不采用此方案；保留真实原生连接未恢复的限制。

## 影响

离线 SSH 的重复读取不会形成连续连接尝试，慢远端读取与本机操作得到隔离，手机可以继续刷新本机已落盘内容。代价是进程内退避状态、主机级操作门锁以及被动读取缓存；离线主机的自动恢复最多等待退避上限，用户可手动提前检查。

Bridge 的退避不修改或接管 Codex 原生应用自身的 SSH 重连定时器。现场原生日志也存在远端连接超时与重试，因果关系仍需原生恢复后的对照复测。不能承诺本次源码修改已经修复原生 IPC 的 `no-client-found`，也不能把缓存历史可读等同于发送可用。

SSH 修复已编译、签名并覆盖安装到 Mac Test `2.1.7-test.20261030.ssh1`，基于当前 `38bd865` 及本轮未提交变更。正式版 8787、Codex 本体、账号绑定和 Test 连接配置均保留；没有强杀、推送或发布。Windows、Linux 和手机安装包未在本轮更新。

## 验证

### 关闭请求的排队与阶段耗时

8796 的历史日志没有记录关闭接口及阶段，不能追溯确定用户那次等待分别花在哪一段。当前保存的桌面候选历史为 564 条，元数据只读扫描约 0.040 秒；独立 IPC 连接约 0.9 毫秒。三个只读 owner 查询分别给出 0.1 秒请求期限，却均耗时约 1.10 秒，因为客户端等待额外保留一秒传输宽限。此结果证明逐条任务审计在大量历史下可能触及总预算，不证明这些会话空闲，也不证明用户那次退出必然由此导致。

隔离生命周期夹具复现同主机连接持有操作门锁时关闭请求持续排队。修复前，0.5 秒观察期内没有结果；修复后，默认两秒排队上限实测 2010.7 毫秒返回明确拒绝，原生退出调用和任务审计调用均为零，启用偏好不变；解除占用后的显式重试仍执行完整即时核验。证据仅含合成结果，位于 `.tmp/close-latency-20261107/bounded-gate.json`。103 项客户端生命周期测试、3 项门锁测试和模块边界检查通过，覆盖嵌套排他、超时后门锁状态保全、后续重试及原有活动任务阻拦。

本轮没有退出真实 Codex，也没有使用展示缓存替代安全证据。全量审计原有约二十秒预算、原生正常退出原有约二十五秒等待保持不变；这些是既有上限，不是本轮实测的正常退出时长。真实闲置 App 的完整关闭耗时仍须在无活动任务时验证，不能根据隔离夹具宣称已通过真实退出验收。

### 安装与 SSH 离线下的真实交互

安装过程先核验活动任务、消息提交记录和进程身份，再正常停止 Test 网关并退出 Test 外壳。旧包及私有数据备份保留在 `.tmp/ssh-isolation-20261030/mac/`，构建输入哈希、签名核验、配置保全及实际安装结果分别记录在 `build-result.json`、`install-result.json` 和相关保全文件中。正常退出之后两个已退休的 Codex crashpad 子进程自行结束；按 PID、启动时间、父进程和用途核实后，仅将这两个无关旧子进程从安装保全比较中排除，没有终止它们或当前 Codex。

用户已登录的专用测试聊天完成以下验收：账号管理显示 SSH 离线；手动重试后探测仍处于检查中时，局域网会话约 1.6 秒重连完成。只发送一次不使用工具的确认消息，正常取得回复、草稿清空。SSH 随后回到退避，连续失败的等待延长至分钟级；只读账户查询不会绕过退避。证据为 `manual-ssh-local-reconnect.json` 和 `offline-local-send.json`。

HTTPS 同一测试聊天只发送一次新的确认消息，发送接口 HTTP 200，约 7.48 秒收到回执，模型回复、草稿清空，局域网页面也显示同一条回复。HTTPS 刷新首次等待超过浏览器工具十五秒期限，稍后页面完成、恢复已连接并显示最新回复，草稿为空；因此发送正确性通过，公网加载延迟和间歇错误仍未消除。证据为 `offline-https-send.json`、`offline-https-reload.json` 及 `https-diagnostic/browser-requests.json`。此前结果未知的测试消息已经由提交记录 `accepted` 和两端实际回复确认；新测试没有重放该旧消息。

### Codex 更新与 IPC 路由切换

用户提出“Codex 更新后自动重启，网关仍保持旧连接”的假设。对齐原生日志 UTC 与网关/VS Code 日志北京时间后，确认以下顺序：10 月 29 日 20:25:12 原生更新安装开始，20:25:24 新 Codex 进程启动；20:25:52 正式版和 Test 都记录 `desktop_owner_attached`，随后持续成功连接，23:58 仍有成功记录。因此更新后一直未重连的解释与日志不符。

10 月 30 日 00:07:06.853，VS Code 扩展宿主收到退出消息；00:07:07.391 记录 PID 59602 正常退出。此扩展此前承担共用 Codex IPC 路由。00:07:07.524–.529，两个网关及 Codex 内部同时记录 IPC 断开/重置；00:07:08.544，Codex App 开始承担路由。此后新建的独立 IPC 客户端可以初始化，但活跃本机会话查询经过十秒返回 `no-client-found`，没有快照。这不只是网关缓存旧 owner。用户在 01:08 手动重开 Codex 后，原生 owner 和快照恢复。重开前正常退出请求未能及时结束进程，本轮未强杀、未绕过 Computer Use 对 Codex UI 的限制。

在项目临时套接字上提取当前安装版的 `IpcRouter`、`IpcRouterManager`、`IpcClient` 路由逻辑进行隔离复现，消息帧和文件操作使用最小适配，未运行或改写真实应用。旧路由退出后，五个客户端的独立 router manager 同时通过“不存在可连接端点”的检查；随后的删除旧 socket 操作可以删除另一个刚创建的可用 socket 路径。实验保留五个活动路由，五个客户端均初始化成功，但全新的外部客户端查询五个已登记 owner，仅一个成功、四个为 `no-client-found`。这证明该原生代码存在路由创建竞态与会话不可达机制。

同一复现只把路由创建合并为一个在途操作，对照得到一个活动路由、五个 owner 全部可达。此为隔离机制验证，不是已应用的原生补丁，也不能据此声称掌握历史故障瞬间每个内部 socket 的分布；现场时间线与症状高度吻合，但未保存当时的完整路由内存快照。普通“Received broadcast but no handler is configured”在健康状态也大量出现，不作为根因证据。复现脚本和结果为 `reproduce-native-router.cjs`、`native-router-race.json`、`native-router-control.json`，时间线为 `update-timeline.json`、`bridge-transition-timeline.json` 和 `vscode-ipc-transition.json`。

新增真实 Unix socket / Windows pipe 夹具回归验证 Bridge 自身在路由正常重建时可以保留网关进程、重新初始化、发现新 owner、取得最新快照并向新 owner 发送一次；没有激活其他会话或重放写入。与 SSH 阻塞下本机重连用例共两项在 macOS 通过，Windows pipe 分支未实机执行。原生路由的并发创建缺陷尚未永久修复；本轮不改 Codex 安装包、不让 Bridge 接管路由或另起 app-server 接管 Desktop 聊天。

### HTTPS 回执与访问路径

原生重启后、安装本次修复前的一次 HTTPS 测试已实际执行并回复，但浏览器发送请求返回状态 0 / `Failed to fetch`，草稿保留；服务端记录为 `accepted`。本次新包的独立发送收到 HTTP 200，但其他只读请求仍出现 502、520 及未被 AbortSignal 取消的 `Failed to fetch`。因此旧回执失败不能解释为原生拒绝执行，也不能认为安装后网络故障全部消失。

当前系统 HTTPS 代理为本机端口 15937。相同公开静态资源进行三组无认证对照：直连均 HTTP 200，约 0.46–0.59 秒，Cloudflare 回应节点 SIN；经当前代理均 HTTP 200，但约 9.32–13.44 秒，回应节点 ATL/EWR/CDG。浏览器中的账户和会话只读接口还曾等待约二十六至三十秒后收到 502/520；仅 `/api/clients` 的十秒超时属于前端主动取消，其他失败不是同一原因。此结果证实代理路径显著放大延迟，支持传输路径异常的判断；三次静态资源对照未复现状态 0，不能将旧单次发送失败确定归因到代理服务的某个内部环节。

本机固定隧道的观测窗口内维持四条连接、请求错误计数为零，收到的请求返回 200；这不能单独证明所有失败请求均到达隧道或排除其他 Cloudflare 边缘问题。未改系统代理、DNS、Cloudflare 配置或访问控制。证据在 `https-diagnostic/`；最后一次在同一浏览器诊断连接中采集页面重载，收到 381 条底层事件，未捕获失败请求，不能追溯解释旧回执错误。完整链路稳定性与真实手机公网使用仍未验收。
