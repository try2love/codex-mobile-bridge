# Agent Note: Git 历史按需读取

Status: implemented

## 问题

远程工作台打开 Git 子页面时，`git-status` 使用 `status --untracked-files=all` 一次枚举当前项目的所有未跟踪路径。大型仓库的结果超过 Git 读取上限后，整个页面只显示“Git 变更列表过大或不可读取”，即使提交历史本身仍然可以读取。

## 决策

Git 面板默认先加载提交历史。历史查询只准备仓库边界和 `HEAD`，然后使用现有的最近 40 条查询和“加载更早的提交”分页；提交详情也不依赖工作区状态枚举。变更列表仍保留为显式模式，因此暂存、差异和提交操作继续使用完整状态与版本指纹，不能把截断状态当成可操作状态。

## 备选方案

提高 `git-status` 的输出上限只能延后失败，并会继续把大量路径传输到手机。把状态输出截断后展示部分文件会让用户误以为列表完整，且会使暂存和版本校验不安全。单独增加一个复杂的 Git 历史缓存会引入失效和权限边界；现有历史接口已经支持有界分页，因此复用它。

## 影响

首次进入 Git 子页优先显示最新提交，加载更早提交仍按 40 条递增。后续[大型 Git 变更分页](2026-11-22-large-git-status-pages.md)消除了变更模式的原始输出上限，并以完整状态指纹保护分页操作；历史仍不依赖工作区扫描。仓库元数据读取新增一次轻量的 `rev-parse --verify HEAD`，不触发工作区扫描。

## 验证

回归夹具生成 23,000 个未跟踪文件，使状态输出超过 2 MiB；在同一仓库中历史和提交详情仍成功读取。GitWorkspace 22 项测试、浏览器 Git 面板单元夹具和 Playwright WebKit 最新提交/分页测试均通过。
