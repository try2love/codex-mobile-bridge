# Agent Note: Antigravity 停止期间拒绝迟到工具并保留待发队列

Status: implemented

## 问题

`request_stop()` 清除心跳后，迟到的 `pre_tool_use` 仍会在分派入口恢复心跳；自动允许分支也仍允许工具执行。停止发生在审批对象构建与注册之间时，请求尚未登记，原有停止逻辑不能唤醒它。另一个时序中，停止后的 `post_invocation` 过早清除标记，随后的 `fullyIdle/model_stop` 会消费队列并自动继续。

## 决策

- 停止标记存在时，Hook 分派不写入心跳。权限快捷分支与审批注册在锁内检查停止标记，迟到请求统一返回拒绝。
- 被停止的审批对象保留 `stopped` 状态。即使后续显式请求已清除会话标记，旧审批等待线程仍返回拒绝，不恢复心跳；迟到的用户允许也不能覆盖停止事实。
- 停止标记保留到显式 `begin_user_turn()`。`post_invocation` 返回 `terminationBehavior: terminate`；原生 `stop` 事件只清心跳并返回，不消费 `queue` 或 `steer` 内容。重复终态和迟到的工具请求不能恢复队列或工具执行；后续用户明确继续时恢复原有处理。
- 原生强停成功但不发终态 Hook 时，适配器仅在确认原生空闲、无待交互，并完成显式用户请求的内容校验后，紧邻 `send`、`goal` 或 `compact` 的原生发送调用 `begin_user_turn(key)`。该入口只清除目标会话的停止标记，不更新心跳、不消费队列，也不解除旧审批对象的停止状态。被动读取和工作模式设置不调用此入口。

已有[整树停止记录](2026-11-16-antigravity-stop-tree-and-concurrent-stop.md)仍负责原生 RPC、来源识别和前端并发停止。本记录与其部分重叠，只补足 Hook 停止时序；没有完全吸收或移除旧记录，也不调整其他提案。

桌面端新轮次的自动恢复由[原生控制核验](../feature/2026-11-19-antigravity-native-controls-reviewed.md)补充：仅首个 PreInvocation 且有效原生步数严格推进时可解除停止；终态回执或缺失计数仍不能独立解锁。本篇关于旧审批、队列和显式网关发送的约束继续适用。

## 备选方案

只在审批等待返回后检查会话停止标记，改动较小，但不能覆盖自动允许、尚未注册的审批以及后续显式请求先于旧等待线程恢复的情况。在终态回执清除标记可以尽早解除限制，但重复或迟到的同一轮 `model_stop` 会自动消费队列，因此标记保留到显式 `begin_user_turn()`。

## 验证

- 修改前，新增的五个测试产生六个断言失败；正常审批用例通过。
- `python3 -B -m unittest discover -s tests -p test_antigravity_stop_hooks.py -v`：八个测试通过，覆盖三权限模式、审批注册竞态、显式新轮次与旧审批唤醒竞态、迟到允许、重复终态、队列保留和后续继续。适配器用例还验证无终态 Hook 时显式空闲 `send/goal/compact` 恢复下一次工具请求，旧队列不自动消费，忙或等待状态不清标记。
- 既有 `test_antigravity_hook_delivery.py` 三个测试通过，队列发送结果未知不重放的约束保持。
- 本记录以本地定向回归验证 Hook 时序，未操作真实客户端；完整接入回归和原生停止行为由集成验收另行报告。

## 影响

停止期间的工具请求拒绝执行，心跳保持清除；排队消息保留，正常审批及自动续发逻辑不变。增加的审批状态仅存内存，不改变 IPC 或磁盘格式。停止标记只通过已核验空闲的显式用户发送解除，不依赖终态 Hook 的数量或超时推测任务已结束。未操作真实客户端。
