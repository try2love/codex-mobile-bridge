# Agent Note: Claude 原生历史不应依赖可读的账号库

Status: implemented

## 问题

[Issue #127](https://github.com/try2love/codex-mobile-bridge/issues/127) 的三个问题有不同边界。Windows MSIX 进程可报告名义配置路径，开发者设置却位于包重定向目录。macOS 和 Windows 的文件连接器首次初始化、且无可复用会话时，确实以空消息调用原 App。还有一个独立的共享缺陷：原生历史已返回，补充模型目录身份时读取官方账号 Cookie 库的异常却使整条详情失败。

在 Windows 笔记本用拒绝共享的文件句柄，在 Mac 和 Ubuntu 用 SQLite 排他事务，分别锁住合成账号库。三端共享函数均表现为：未锁时列表与详情成功；加锁后列表成功、原生详情已经返回、网关详情失败；解锁后恢复。未操作真实账号，也未测计费。Linux 正常支持的 Claude CLI 不调用该 Desktop 账号路径；共享函数的实验不等于 Linux 原生 App 复现。Windows 配置发现的夹具还复现了“唯一进程名义路径”遮住实际启用开发者模式的包目录。

## 决策

把会话历史和账号绑定能力分开。已核验的原生历史可显示；账号身份无法确认时，不复用其他账号缓存、恢复账号草稿或切换模型。原生模型列表本身不能证明账号身份。Windows 的目录映射须核验实际包族；证据矛盾时保留显式配置入口。首次初始化只复用同目录已有会话。没有这些会话时，先用 Claude 的 checkTrust 核验目录，再用其本机暂存文件接口交付加密回执。两个分支都不调用 start 或 sendMessage。

## 备选方案

退出客户端可能释放文件锁，同时也中断了用户要继续使用的桌面客户端。复制运行中的库、解除锁或直接取消账号校验，都不能保证缓存和草稿属于当前账号。继续传空字符串实现最短，但原 App 有权按新消息处理，不能保证不消耗额度。

## 验证

合成官方账号锁库前后的对照覆盖原生历史、模型、模型写入拒绝与身份恢复。独立运行生产连接脚本和 Python 接收端，已信任的空目录完成握手和列表查询，模型启动和发送计数均为零。未信任目录只报告原生信任要求。

## 影响

不同版本的 Claude 原生能力有差异。报告中的真实空回复是 Windows 现场证据，不代表各版本的计费记录。用户手工修改配置后的编码错误发生在启动阶段，与原版详情报错分开处理。

原生暂存目录只接收当前网关标识对应的普通文件。回执用网关绑定密钥派生的 AES-GCM 密钥加密，进入原有签名、代际及序号校验。一份回执得到确认后才写下一份。网关接收后删除自己的密文，原 App 用户附件不参与清理。Linux CLI 继续使用其原生协议。
