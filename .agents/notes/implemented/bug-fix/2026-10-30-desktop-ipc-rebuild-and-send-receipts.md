# Agent Note: 桌面 IPC 路由切换后的远程重建与发送回执恢复

Status: implemented

## 问题

[SSH 离线隔离与原生路由诊断](2026-10-30-ssh-offline-isolation-and-backoff.md)已分离两个故障：SSH 离线曾阻塞其他主机操作；原生 IPC 路由切换还可能留下可通信但找不到目标 owner 的旧连接。已有“重新连接”复用旧 socket，不能摆脱这种连接；等待结束的提示也没有可执行的远程恢复入口。

HTTPS 的另一条故障链是原生已接受消息、服务端记录 `accepted`，但浏览器收到 `Failed to fetch`。原回执查询可以清除未确认 ID，却没有同步已提交的草稿，页面容易仍显示未发送。浏览器既有状态轮询也没有持续触发回执核对。

## 决策

Bridge 为本机 Desktop 会话提供显式 `reconnect` 请求 `{activate:true,rebuild:true}`。此请求经过既有登录、CSRF、会话主机及操作门锁；只替换 Bridge 自己的 follower 连接，重新初始化、发现 owner 并等待真实快照。所有写操作仍保留原生 owner、provider、认证和 cwd，不启动替代 app-server，不重放未知写入。被动读取不导航、不自动重建整个连接。

普通显式接续也复用同一重建实现。Unix 连接记录公开 socket 的设备及 inode；显式接续时检查入口是否已被替换，不增加后台轮询。若入口变化但旧连接仍标记为已连接，先沿旧路由请求当前快照：原 owner 仍响应就保留；没有取得快照才替换 follower。已确认 owner 断连时也最多替换一次，Windows 命名管道复用这条断连恢复路径。一次接续中的显式重建不再二次换线，后续等待原生会话仍沿用原有有界逻辑。

HTTP `reconnect` 通过 `Bridge.reconnect_session` 在主机操作门锁之前合并同一聊天、同类参数的在途请求；并发调用共享成功或失败，不把一次故障排成多轮激活。局域网与 HTTPS 使用同一入口，写请求和回执语义不变。WSL 接入不是 `Bridge` 的 Desktop follower，仍调用其既有 `activate`，不把 IPC 换线套到 WSL 原生运行时。

连接失效或 owner 请求失败时，会话返回 `rebuildRecommended`，共享 Web/手机页面显示“重建连接”及保留历史和草稿的提示。显式连接等待有界，失败后结束忙碌状态并保留恢复入口；成功快照清除建议。重建按主机串行等待既有写请求完成；其他被关注的本机会话重新跟随同一新连接，Codex 中的任务继续执行。旧 reader 的回调和退出必须核验 socket 身份，不能让迟到事件覆盖新连接状态。

重建失败后保留“重建连接”，旁边单列“应用管理”。传输已重新建立但 owner 仍未恢复时，明确显示已做过重建并提示应用管理兜底，不只建议反复重试；更换传输本身就失败时仍允许再次重建。重启应用须主动进入应用管理，仍受活动任务核验约束。回归覆盖第一次重建失败后，原生任务和网关均不重启，第二次重建连接成功。目标会话的已保存内容和实时控制权限分别判断，历史仍在更新无法单独证明写入可用。

发送回执恢复复用共享 `ComposerDrafts`、`MessageManagementBinding`：新提交在等待 IndexedDB 协调锁之前固定草稿 revision，按原请求 ID 只读查询。账号与会话身份一致、记录版本未变化且回执为 accepted/queued 时，清除同一 revision 的已提交草稿和当前输入状态。用户后续编辑、旧版无 revision 的草稿、未知结果均保留。核对回执不执行发送、排队或接管；同一记录的只读重查从一秒递增到最多三十秒，新记录立即可查。成功核对解除旧网络错误，不能把失败写请求直接当作成功。

## 诊断与验证

故障夹具保留旧 Unix 路由进程及已连接 socket，将新路由绑定到公开入口。修复前重建 API 缺失；修复后 Bridge 接上新路由，读取新快照且没有发送 follower 写操作、退出旧服务或导航其他聊天。旧 reader 延迟退出、找不到 owner 后的显式失败、未授权重建和非显式参数拒绝都有回归。

显式接续的新增回归先复现旧快照仍为 connected 时直接返回退休路由、owner 断连后不换线两种失败。修复后，真实 Unix socket 夹具覆盖公开入口换代后接回新 owner、旧 owner 仍回应时保留连接、断连后只重建一次、等待同主机在途操作结束以及三个并发重连共享一次失败；未知写入仍仅发送一次。与 HTTP 登录/CSRF、SSH 主机隔离和 CLI 原 owner/后台接续边界合计 23 项定向回归通过。该结果是隔离协议验收，没有退出真实 Codex 或 VS Code，也没有发送模型请求；不代表新版安装包或原生隔离故障已完成实机验收。

不含云接入的 v2.2.0 候选组合中，上述 23 项与客户端生命周期 103 项、门锁 3 项合计 129 项定向回归通过；模块边界检查通过。恢复和关闭共用同一操作门锁，没有因提取共性修复而引入云鉴权、云草稿身份或云路由依赖。

协议专项 111 项运行通过（2 项平台跳过），SSH 隔离、CLI、消息管理和大快照相关 81 项通过。浏览器合成测试覆盖 Chrome/WebKit 的宽窄屏：注入一次发送响应丢失，确认只有一次 POST，一次 GET 核对 accepted，旧草稿清空、新草稿不丢失。前端测试夹具已补齐回执回调依赖；另先复现等待协调锁期间编辑的新草稿被误清理，再将 revision 捕获提前到等待前，新回归验证该窗口也保留后续编辑。以上夹具不冒充公网自然故障已消失。

## 备选方案

重启 Codex 能让原生 owner 重新登记，也是此前临时恢复的有效办法，但会干扰原生工作且不能形成网关的恢复能力，用户明确要求不再依赖它。修改原生安装包中的 router manager 能针对其竞态，却越过当前授权与升级边界，因此不采用。

只重复 owner discovery 最少改动，正常冷启动确实能恢复；当 socket 仍连着退休路由时，无论重复多少次仍到达旧路由，因此增加显式替换本端连接。全局自动反复断连会影响其他会话且不保证抵达原生孤立 owner，故不采用。

公开 socket 变化后立即断开旧连接实现简单，却可能放弃一个仍能响应的原 owner，使可用聊天失联。因此先索取当前快照，再决定是否替换。把请求合并放进主机门锁内部也更直观，但重复调用已经排在锁外，不能消除多轮等待；连接请求在 HTTP 的共享 Bridge 入口合并，实际恢复继续受原门锁保护。

网络失败后自动重发最容易让输入框消失，但请求可能已经执行，会造成重复操作；仅按原 ID 核对回执可以确认执行状态。无条件清空草稿也容易实现，但会丢失发送期间的新编辑，因此只清理已记录的原 revision。

## 影响

用户可以从远端摆脱 Bridge 持有旧路由连接的状态，不必重启 Codex；真正未恢复时仍能看到有限、可操作的失败结果。回执恢复减少假性发送失败，增加少量有退避的只读请求和一项兼容旧记录的 revision 元数据。

显式 Unix 接续增加一次本地入口身份读取，入口变更时增加一次只读快照确认；重复请求仅共享在途结果，不缓存失败、不增加常驻监听。连接替换仍可能让本 Bridge 的其他 follower 短暂重新跟随，但不会结束原生任务或接管执行。

Bridge 无法通过公开 socket 找回已被原生路由竞态隔离在未链接 socket 上的 owner。当前集成只有 owner 发现、follow 和已有桌面深链，没有可调用的原生 owner 回迁操作；若当前入口本身也没有目标 owner，换线和深链后仍会明确失败，应用重启仍是核验任务后的最后兜底。此限制与原生竞态的隔离复现保留在前述记录，不能声称完全修复 Codex 内部路由。HTTPS 传输的历史丢失环节也须独立取证，回执核对修复不等于网络稳定性已验证。

不更改 Codex 安装包，不停止或重启 Codex，不改正式 8787、代理、DNS、Cloudflare 配置及 DSH 插件；本轮仅本地开发及 Test 安装，不推送或发布。

## 原生开始执行回执超时的持久证据恢复

RC2 的真实 HTTPS 消息返回 `thread-follower-start-turn-timeout`。浏览器收到 HTTP 409，网关日志 `written=True`，服务端耗时 5024 ms；原生 rollout 的 `item_completed/UserMessage.client_id` 及历史索引 `userMessage.clientId` 均包含同一提交 UUID，且任务已经完成。因此这条样本的丢失点是原生 follower 的开始执行确认，不是 HTTP 响应在公网丢失；此前 Cloudflare 样本仍保留各自结论。

辅助函数留在历史读取模块，保持消息管理源码可独立下发，不引入远程机器上的 Bridge 包依赖。Bridge 仅凭同线程的原生持久用户项 UUID 将既有 `unknown` 更新为 `accepted`，落盘失败回滚状态。共享消息管理仍只读 ledger，不重发，不在查询入口附着 owner。已连接页面按未知 ID 集合与最新已完成 turn 合并后台读取：同一状态最多读取四次，首次之后按 2/4/8 秒退避，为持久化落后或瞬时读取失败留出恢复机会，不无限轮询；重复回执 GET 本身不读历史，没有未知消息不增加读取。读取复用现有两轮/四十项窗口与 rollout 缓存，不扫描整段历史。超出窗口的旧消息仍保留未知，加载对应历史后才能确认。

原生实时状态不能当证据：App 会先插入尚未成功执行的 prepared turn；Bridge 也可能从 params.input 生成显示行。按正文比对、按助手回复猜测或把错误直接改为成功都会误确认，所以不采用。索引缺失时，仅保留同线程、同 turn 的原生 UserMessage 完成事件 ID，复用已有 response_item 显示正文，避免重复气泡。排队、忽略、撤回及不存在的记录都不改；读取期间用户忽略后，落盘前重新核对仍保留忽略。

针对性回归覆盖持久证据确认及重启、实时 prepared 数据拒绝、跨线程/主机/无效 UUID 拒绝、队列状态保护、并发忽略、写盘失败回滚、连接中读取合并和 fallback 不重复正文。最终安装包与公网复测结果单独记录，不将源码测试冒充最终包验收。

## 2026-11-10 原生路由移交与恢复时延

当前版本在空闲合成聊天上完成一次真实 VS Code router 正常退出的状态验收。用户先确认编辑器文件已保存且无任务；只通过 VS Code 自己的正常退出关闭原主进程 54821 和扩展 router 54852。正式 Codex App 25292 的进程世代、provider、账号和 cwd 不变，没有发送模型消息或审批操作。

选定聊天只有空合成历史。网关在北京时间 01:29:56.829 记录 `desktop_ipc_disconnected`，01:30:14.564 收到原生快照并记录 `desktop_owner_attached`，中断约 17.735 秒；01:30:22 的网页采样已显示“已连接”。期间没有刷新、重建或重启 Codex。公共 socket inode 从 103804253 换为 103966870，新的 router 属于原 App 25292。原生 App 日志在 01:29:56.832 记录 reset，01:29:57.841 已有新 client 事件，证明路由约一秒后已可通信；原日志没有完整记录该聊天 owner 最早可发现的时刻，不能把剩余全部时间直接归因于原生 owner。

重新打开独立 VS Code 后，日志和 webview 均确认 Codex 扩展已激活，网页保持已连接。随后正常退出测试编辑器，恢复用户原 VS Code（新 PID 15629），其 Codex 扩展在 01:33:24.911 激活，网页仍保持已连接。打开场景没有发生原 App 到 VS Code 的 router 反向移交，因此不推广为任意启动顺序均已验收。旧版“换线后持续 no-client-found、只能重启 App”的故障本次没有复现；17.735 秒可恢复中断则已经复现，仍需要减少。

### 恢复期限

`_refresh_async` 成功后不再保留失败重试期限。收到真实 IPC 或原 owner 断开事件时，清除对应旧期限并递增 `connection_epoch`；旧 probe 晚返回只可在相同代次写回期限，不能覆盖新失效状态。activity、notification、普通 refresh 和维护器共同写入的期限均与失效处理共用 `session.condition`，避免计算旧值后覆盖清零。

断开后的六秒内，失败 probe 使用半秒的短期限，维护器保持原三秒扫描，不扩展为六秒或十二秒等待。窗口结束后仍使用原十五秒失败退避和原维护退避，没有新增后台高频循环、常驻线程或唤醒机制。真实快照仍是“已连接”的唯一依据；不隐藏断开状态，不激活聊天、不另起 writer，也不自动重放未知写入。原服务长期不可用、原生请求自身超时或窗口外故障不保证三秒恢复。

### 验证边界
