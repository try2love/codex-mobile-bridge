# Agent Note: 显式继续会话时复用尚未完成的执行归属查询

Status: implemented

CLI 不再发起 App owner 查询，见[来源执行路由](2026-11-11-codex-source-execution-routing.md)；下述 owner 等待与代次规则继续用于 IDE，原生 daemon 启动去重保留。

## 问题

对源自 CLI 的聊天执行显式继续操作时，会先发起后台执行归属查询，再同步重复同一次查询。如果后台查询已进入缓慢的 `IPC.owner` 调用，第二次调用会在原生继续操作或 Desktop 执行归属错误之前再增加一次等待。另外，原生代理连接失败后，启动守护进程前也会重复同一次连接尝试。

## 决策

显式继续操作等待当前后台执行归属查询完成，并且只消费一次结果。若当前没有查询，则仍发起新的查询。后续独立的显式操作也会重新探测。后台保存历史读取独立进行。原生适配器还会在第一次连接前记录守护进程的启动代次；取得锁后，仅当其他适配器调用在此期间启动了守护进程，才重试代理连接。身份检查和禁止重放写入的规则保持不变。

CLI / IDE 的在途查询等待上限为 20 秒，覆盖一次冷连接的 socket 连接 5 秒、initialize 5 秒加 1 秒回执宽限、owner 查询 6 秒加 1 秒宽限，以及最多 1.5 秒快照等待；桌面来源维持原 8 秒等待。等待条件一旦成立便立即继续，不增加固定延迟。超过预算只返回连接检查未完成，不另发查询或启动原生接续；尚未结束的后台查询继续保留，后续操作仍复用它。网关关闭时唤醒等待者。

同步读取和后台读取还可能在同一会话的 `attach_lock` 排队。只复用等待此锁期间、同一 `connection_epoch` 已完成的 owner 查询；用独立的完成序号及该查询的起始代次识别这次重叠，保存历史更新不会充当查询完成证据。旧代查询完成时不能覆盖新代 owner 状态，也不能推进新代可复用的完成序号。连接失效后或后续独立进入时仍重新查询。此规则只合并只读归属发现，不合并发送、审批或停止操作。已有 CLI 超时兼容判断及 found / unknown 拒绝路径均保持原样，不因为延长等待而放宽归属判断；相关边界见[原执行归属记录](2026-10-14-cli-existing-owner.md)。

## 验证与限制

在真实 `Bridge.activate` 调用链中注入延迟的模拟 `IPC.owner`，修改前在不存在执行归属进程、以及已有归属进程但尚无快照这两种情况下都会查询两次。修改后只查询一次；后续独立激活仍会重新探测。受控的代理不可用夹具所需尝试从三次降至两次。隔离的原生 0.162.1 冷连接在修改前后都约为 0.25 秒，因为该夹具不存在代理停滞。夹具测量证明了重复等待，但用户报告的生产延迟尚未在实际 IPC 边界计时。

2026-11-11 的真实长度前缀 IPC 帧夹具使用隔离 Unix socket 和真实 `DesktopIPC` / `Bridge.activate`，不启动原生 daemon、不调用模型。initialize 在 4.306 秒响应，owner 在 8.608 秒明确返回 `no-client-found`；修改前显式继续在 8.009 秒提前报“桌面连接检查未完成，请稍后重试。”，此时查询仍在途。修改后相同延迟在 8.609 秒收到结果、8.614 秒成功接续，owner 查询和 CLI attach 各一次。8 秒外层限制由 `25bd5c48e1b6a8b1d54e416457a131dbd62b3b3c`（2026-10-30）加入，短于下层单次完整冷查询预算，并非此次账号 / provider 变更引入。

定向回归还覆盖：同步读取持锁时后台查询排队，修改前重复 owner 两次、修改后一次；多次后台刷新及显式等待超时不增加在途查询；关闭立即结束该条件等待；found 无快照和 unknown 不启动 CLI；IPC 已就绪且明确 absent 的正常路径不增加等待。旧代查询持锁、断线递增代次、新代读取排队、旧代才返回 absent 的受控顺序，确认旧结果不覆盖新代状态，新代必须重新查询。单元夹具证实排队会重复查询，不能据此断言用户现场一定发生了该排队。共享 IPC 的 `connect_lock` 或其他主机读取仍可能占用预算；超出该条件等待上限时保留待核验状态。

## 备选方案

每次重新探测可以保证信息新鲜，但会重复同一项尚未完成的观察。仅复用当前查询可以消除这次延迟，同时后续用户操作仍会获取新的执行归属证据。

只把 8 秒改大能够覆盖已复现的冷初始化，却不能消除 `attach_lock` 后的重复 owner 查询，因此同时合并实际重叠的只读查询。不设置上限会让锁竞争或异常端点长期阻塞显式操作；超时后直接接续则把未完成观察变成接管许可，本次均不采用。

## 影响

继续操作仍需等待真实的执行归属查询；本次修改不放宽归属身份检查，也不引入基于超时的接管。

冷启动允许等待完整单次查询，该在途查询的条件等待上限从 8 秒增加为 20 秒；正常完成立即返回。此上限不是整个 `activate` 的总预算：后台刷新因冷却跳过时，原同步 `_attach` 分支仍可能等待 `attach_lock`，本次不改该旧路径；关闭唤醒也只覆盖这里的条件等待。此改动不取消已经派发的读取，不停止共享 daemon，不变更原 owner / provider / auth / cwd。真实 App 的冷会话点击时序和跨平台行为仍须各自实景验收，协议夹具不能替代生产现场结论。
