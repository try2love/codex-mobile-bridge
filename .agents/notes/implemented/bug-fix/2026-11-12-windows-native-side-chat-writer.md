# Agent Note: Windows 侧边聊天复用原 App 的原生 writer

Status: implemented

## 问题

Windows 原 App 已持有父聊天时，另起元数据运行时会触发 `already has an active writer`。Mac 的共享 Unix transport 不能直接照搬：Windows App 关闭 stdio 子进程时会直接结束适配器，Python 的 `finally` 不保证执行，独立原生服务可能遗留。

## 决策

Windows 默认本机 Desktop 初始化复用现有账号面板、任务核验和正常重启流程。原 App 通过已支持的 CLI 路径配置启动透明适配器；适配器持有原生 stdio 的唯一输入写端。原 App 保留唯一初始化、审批和任务控制权，原始 cwd、账号、provider 与 CLI 参数保持不变。Bridge 仅通过私有命名管道访问既有侧边聊天和元数据操作，不建立第二个 writer。

`DesktopStdio` 将 App 和 Bridge 请求映射为互不冲突的内部 ID，原生输出只读一次。通知与服务端审批请求继续交给 App，Bridge 回包只交给原调用；超时、迟到或未知回包不会被重放。消息容量核验包含 ID 扩展，单条超限只拒绝该请求，不断开原 App。Bridge 白名单仅包含 fork、list、inject_items、name/set、read、backgroundTerminals/list 和 delete。

命名管道复用 `local_rpc` 与 Windows `local_service` 的私有记录、令牌、同用户与桌面会话以及精确进程身份校验。每次调用重新核对 App、适配器、原生进程和配置目录。原生错误保留完整 RPC 结构，继续使用共享错误转换。只有首个业务请求明确尚未发送才允许安全重试；此前已经成功或结果未知的请求不会因后续连接拒绝而整体重放。

适配器退出后，操作系统关闭唯一 native stdin 写端，原生收到 EOF 执行连接和线程清理。正常路径关闭管道并等待原生退出；超时保留运行记录，不强杀。App 直接结束适配器时遗留的记录必须按原生进程出生时间验证；已退出但 PID 仍存在的 Windows 进程句柄不被误判为活动运行时。

初始化在停止 App 前核验冻结启动器以及安装登记的 MSIX package family。启动时恢复原 App 因自定义 CLI 路径而移除的已核验 sandbox family，不接受任意调用者提供的替代值。网关可执行文件路径改变后，需要重新初始化，不能静默使用另一程序。Windows 配置记录放在 home 的专用子目录，避免私有目录权限操作影响整个原配置目录。

共享启动还必须保留调用者的环境。Store App 使用现有注册、manifest 与 AppExecLink 三重核验的执行别名；准备前核验别名，启动时再次核验，不允许回退 Explorer 激活。普通启动保留已有行为，非打包共享 App 仍直接启动。Microsoft 的[执行别名说明](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-extensions)说明了别名与打包应用的对应关系，具体环境继承以实机验证为准。

执行别名只作为 Windows 实际执行入口，命令行 `argv[0]` 保留所选 GUI 的原路径。`16fc6c3c` 将 `chatgpt-desktop.exe` 同时用作入口和程序名，真实 App 因此选择 `Codex/web/chatgpt-desktop` 窗口目录；随后 `codex://` 协议用原 GUI 名启动，选择 `Codex/web/Codex`，两个主实例均持续运行。相同安装路径不代表相同原生窗口身份。`Popen([原 GUI 路径], executable=已核验别名, ...)` 分离激活入口与程序名，保留原环境、别名核验和取消边界，不改系统协议注册或 App 安装文件。没有通过跳过正常聊天导航来掩盖重复启动。

Windows 的一次性原生命令通过等待子进程完成来转发，显式传递 stdin、stdout、stderr 并返回原退出码。辅助 stdio 调用也显式传递输出句柄。不能照搬 POSIX 的 `os.execve`：Windows 实机上该调用在 UCRT 中以 `0xc0000005` 崩溃，导致 App 的 `--print-startup-config` 收不到 JSON，显示启动策略协议错误。未冻结 Python 的最小调用同样复现，因此不通过调整 PyInstaller DLL 搜索路径处理。主 writer 的路由和所有权规则不变。

就绪以原 App 的 `initialize` 成功响应为准，先核验响应中的配置目录和 App、适配器、原生进程身份，再公布 ready。当前 Desktop 收到该响应即开始读取配置和模型，不发送独立 `initialized` 通知；不能将可选通知当成接入前提。旧客户端的通知仍原样透传，不重复核验或初始化。握手拒绝和身份不符保持未就绪。

创建、权限、幂等账本和成功后的 attached 查询缓存失效继续使用共享业务。Bridge 连接关闭不关闭原 App 或原生运行时，未初始化时明确提示，不回退到独立 writer。

## 备选方案

原生 UDS 加独立 watcher 能复用多客户端协议，但 0.167 第一次 shutdown 进入 drain，等待任务和已接纳请求结束；待审批任务可能一直不结束。再次 shutdown 是强制路径，不能当安全重试。watcher 崩溃也不会给 UDS 服务产生 EOF，因此未采用。

独立 stdio broker 可以继续记录收尾，但本次不需要扩大进程拓扑；适配器自身持有唯一 stdin 已能通过 OS 句柄关闭触发原生清理。原生 follower 未提供 attached fork；修改 App 私有代码、伪造 owner、改历史或用普通 fork 冒充附属关系均不采用。

Explorer 激活能打开拒绝直接 CreateProcess 的商店版，但不会继承这次共享接入环境，不能用于要求保留环境的启动。复用已有执行别名核验，避免修改系统环境变量或 App 安装包。

`os.execve` 在 POSIX 上可保留进程替换语义，但 Windows 实测不适用。仅换成默认 `subprocess.call` 虽能退出 0，却仍丢失非继承的标准输出句柄；显式传递三个标准流才能保留启动配置 JSON 和错误输出，不使用缓冲整段输出或伪造成功响应。

## 验证

Windows 实机使用原生 `0.167.0-alpha.3.2`、全新隔离 home 和 Node 模拟 App，经过产品初始化转发、私有命名管道和元数据客户端，最终 r5 的 17 项检查通过：创建原父聊天、附属 fork/关系、边界写入、Bridge 断开后 App 保持连接、列表刷新后 App 读取并恢复子聊天、正常 EOF 后原生退出码 0、模拟 App 消失后的原生退出码 0、遗留记录核验和下一代重连。没有使用真实账号、调用模型或修改用户聊天。Windows 外层 Job 下的独立生命周期夹具同样观察到退出码 0；不是仅以 PID 消失判断正常退出。

定向回归覆盖请求 ID、App 审批透传、迟到回包、容量、原生错误、明确未发送与未知写入、启动器预检、Windows 进程出生时间以及默认初始化门。原有 Mac 共享运行时和侧边服务 36 项通过；本次没有改变其 transport。独立复审发现的错误类型丢失、扩展后超限及未发送状态丢失均已修正并补回归。

隔离模拟 App 证据不等于真实 Windows GUI App 或最终冻结程序验收。实际 App 初始化、最终包和双端界面仍需单独验证；当前正在承载开发任务的 Mac 正式 App 没有被重启。

`.15` 实机自动准备越过冷启动路径核验后，暴露了上述 Explorer 问题：原 App 父进程为既有 Explorer，子进程为普通内置 CLI，共享 active 记录缺失；已核验安装具有有效执行别名。新增跨 DesktopApp.start 与平台启动层的回归先失败，再在修复后通过，覆盖环境传递、无别名拒绝启动及非打包直启。40 项启动及共享连接回归通过，其中 4 项 Unix socket 检查因沙箱拒绝绑定而单独在允许本机 socket 的环境补跑；模块边界通过。实际别名启动与侧聊创建仍须最终包验收，不能用这些回归代替。

`.16` 真实 App 经执行别名启动后已保留共享配置环境，随后启动策略检查暴露 UCRT 崩溃。修复前冻结入口与未冻结最小 `os.execve` 调用均退出 `3221225477`；修复后源码入口与原生 CLI 的版本输出、启动配置 JSON、错误输出及退出码 2 完全一致。8 项 stdio 定向回归通过。此结果覆盖辅助命令转发，不等于最终冻结包或真实原生侧聊已经通过。

`.17` 冻结辅助探测、启动配置 JSON、二进制标准流和错误退出码核验通过；真实 Desktop 已完成 initialize，后续配置和模型读取成功，但共享记录仍未就绪。已安装 App 的握手代码及日志证明它没有发送 `initialized` 通知；旧隔离夹具主动发送了该通知，因而漏检。此次先用无通知的顺序复现失败，再修正就绪判断；10 项 stdio 定向测试通过，包括握手前禁止元数据调用、成功后可用、旧通知兼容及核验失败保持拒绝。随后 r6 用真实 Windows 原生 0.167.0、全新隔离 home 和不发送该通知的模拟 App，通过 10 项检查：附属关系创建、原 App 读取与恢复子聊天、Bridge 断开仍可用、正常 EOF 退出码 0 及记录清除；未调用模型。最终 GUI App 验收仍单独记录，不以这些结果代替。

`.18` 真实 App 的握手已成功，ready 记录正确，但初始化回执先于 ready 写入约 0.384 秒失败：桌面 IPC 已能连接，原生握手仍未完成。启动准备因此把共享连接核验放入既有 35 秒等待循环；只有只读核验会重试，stop/configure/start 仍各执行一次，不扩展等待窗口。账号切换沿用默认路径；超时保留 pending 回执，不自动重新启动。回归先复现该时序失败，再验证延迟就绪成功和超时不重放；48 项生命周期检查通过。

`.19` 真实连接准备成功，但原生侧聊创建仍返回 active writer，且出现上述两个 GUI 主实例，侧聊验收未通过。按用户要求停止 Windows 原生侧聊验收，保留原生入口和临时侧聊。本次仅修复重复启动，不宣称它已经解决侧聊问题。

启动身份回归先失败后通过，11 项 Windows 启动与 4 项独立配置回归通过。Windows 26.1106.6628.0 实机以修复后的平台函数冷启动，原生窗口目录恢复为 `Codex/web/Codex`，共享握手就绪；两次通过真实系统 `codex://` 打开既有空聊天后，持续运行的主进程均为同一 PID。没有创建聊天、侧聊或调用模型。初次夹具在启动瞬间将未完成初始化的短暂进程计入主实例而提前停止；后续仅观察并导航同一个已启动实例，没有再次冷启动。源码级实机验证与最终冻结程序更新分别记录，不混为同一结果。

## 影响

Windows 增加一个由原 App 持有的适配器和请求 ID 路由，初始化需要正常重启一次。未初始化不运行适配器，不增加常驻扫描。仅支持已核验的默认本机 Desktop；CLI、SSH、独立配置和 Mac transport 保持原契约。原生 EOF 清理不承诺固定时间完成，超时必须保留真实未知状态。
