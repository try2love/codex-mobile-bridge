# Agent Note: 历史传输批次与有界快速解析

Status: implemented

## 问题

三个被选会话约62MB却产生12061个传输条目。每条小记录分别准备、请求、存块和合并；归档以整个回合的消息字典保存内容，逐条合并反复解析和改写同一个回合。计算下载量还预先逐条检查缓存与分块，延长了用户不能开始传输的等待。

## 决策

同一回合和问题时间的连续小记录合成有界包，每包最多64条、约1MiB缓冲。大记录继续单独流式发送，附件仍独立保留。标准归档负载原本支持多个消息，同一包一次合并。只有网关清单与原生归档都声明 recordBatch=1 才启用；旧手机和旧清单继续使用原协议。

批次缓存判断一次读取回合、逐个核验成员版本及完整正文，缺少任一成员就不算完整。日期清理、账号代次、权限、全包摘要和分块摘要保留。客户端在传输时跳过完整内容，不在开始前逐条精算复用量；确认页给出最大下载量。

小于64KiB的JSON记录先做有界快速解析，并沿用 FrameReader 的历史叶子识别、StoredString 预览、完整存储和摘要规则。大记录继续原流式解析。直接返回普通字符串会改变某些下游内容处理，因此快速解析仍调用同一保留策略。固定原始字节分界对比确认最终条目、总字节和内容版本一致。

## 备选方案

取消所有复用并强制覆盖不会减少逐条HTTP和归档事务，还会重传已有附件。把整个会话打成单个大包会增加内存、失败重做和清理颗粒度。保留有界批次、校验与断点，只取消昂贵的前置逐条核对。直接扩大每个HTTP块也无法改善只有几KB的单条内容。

## 影响

批次任一成员变化时可能重传同包其他小记录；大附件仍可独立复用。开始前显示的是上限，实际下载可更少。已有旧清单仍按旧格式续传，新批次从重新准备的清单开始，不修改已发布快照。

同样3000条合成记录：准备2.215秒、3000条目，改批次后0.235秒、50条目。生产HTTP回环校验完整块摘要，13MB从3000次请求降为50次；回环吞吐不等于手机局域网速度。Swift生产归档512条消息从512次事务、2.790秒降到8次事务、0.084秒。

三个原已选会话在同一固定历史分界下，已批次化的准备从19.54秒降到6.13秒，316个记录包、96个附件、59989791字节及全部内容版本一致。这是只读已保存分界测量，不含实时owner尾部和手机网络耗时。

回归包括64条分界、多消息原生提交、成员缺失不复用、大记录流式回退、Unicode全文、旧协议、清理与权限约束。临时真实历史快照仅用于本地只读测量，结束即删除，不进入日志。
