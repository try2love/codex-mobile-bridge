# Agent Note: Linux ZCode AppImage 区分安装入口与运行映像

Status: implemented

## 问题

Ubuntu 的用户级 Test 启动器仍指向旧 rc7；同时，当前源码也只认可同目录带 resources/app.asar 的平铺 zcode ELF。用户已安装并运行的官方 Type 2 AppImage 因文件名/目录结构不符而被忽略。因此换一个临时新版窗口不能独自解决问题，也不能把 `/tmp/.mount_*` 写成永久安装位置。

## 决策

Linux 平台通用 `appimage` 模块只读识别 Type 2 ELF 与 SquashFS 边界。存在已安装、root 所有且不可被普通用户改写的系统 `unsquashfs` 时，只读取一个有界的根目录 `.desktop` 元数据文件。不会执行 AppImage 获取 offset、不会运行 desktop 的 Exec、不会解包或复制原程序。子进程输出限制64KiB、等待4秒，失败只结束这一个自有只读解析子进程。静态结果按原文件身份缓存，文件替换或修改使其失效。具体品牌仍由 ZCode 平台适配器核验，不把客户端判定放进通用格式读取器。

`application` 保留用户安装的原 AppImage 路径；`executable` 是即时核验出的运行映像。运行时关联使用同用户的原文件/FUSE持有进程及其与原主程序共享的内核生命期管道，再核验只读 FUSE 挂载与原生 ASAR 包名。进程名或 APPIMAGE/APPDIR 环境变量不足以单独构成身份依据；实机的主进程已清理这些环境变量。更换源文件、错误用户、错误品牌、缺少对应挂载或出现多个未选择的实例时不选第一个。实例路由可在候选中按已验证 PID 选择，平台层不决定账号/profile归属。

私有管道 holder 保留原 launcher 作为请求身份，在所启动 PID 的运行映像就绪并通过核验后，才把实际映像交给 PipeTransport；原PID被复用或身份变化时拒绝。冷态 launcher 与运行映像不同不再被误判为安装更换；正常退出前后比较稳定的安装文件身份，启动后重新取得运行描述。普通启动和私有启动都执行原 AppImage，不抄入嵌入 desktop 中的 `--no-sandbox` 等参数。清除从网关自身继承的 APPIMAGE/APPDIR/ARGV0 与 TARGET_APPIMAGE，避免父应用的元数据或目标重定向改变所选启动对象。

没有系统解析能力时仍可核验已运行挂载，但不据此承诺冷启动。新初始化在正常退出原 App **之前**拒绝未核验的冷态能力，避免退出后才发现无法重新打开。不自动安装组件，也不要求用户另装辅助应用；未覆盖的发行版保留边界。

## 备选方案

只识别临时挂载 ELF 能快速让当前列表出现，但一退出就失去路径，不能用于持久配置或冷启动。执行 AppImage 的 `--appimage-offset`、提取指令看似便利，却会在扫描时执行目标文件，不采用。完整解包一个额外应用副本占用磁盘并产生第二个程序位置，也不采用。新增内置 SquashFS 库可覆盖没有系统解析器的机器，但会扩大依赖和解析面；本轮复用该验收机已有系统能力，缺少能力时不冒充已验证。

## 验证

固定官方 [AppImage 格式规范](https://github.com/AppImage/AppImageSpec/blob/master/draft.md)规定 Type 2 使用 ELF 与偏移8处 AI\x02 标记；运行时文件系统在 ELF 后。使用本机已安装解析器的官方 `-help` 核对 `-o` 与 `-cat`。实机仅233字节的公开 metadata读取约6ms，AppImage文件stat未改变。当前源码旧逻辑在同一真实安装上返回缺失，修复后读取到3.17.2，安装路径仍为原AppImage，映像为当前挂载，原PID不变。

定向测试覆盖格式/路径、长度/超时、品牌、换行/空格路径、源文件替换、同用户/挂载/内核管道对应、歧义拒绝及按PID选择；还覆盖未确认冷态时不退出原App、正常退出后接受新挂载、PID复用拒绝。Ubuntu 上的原有匿名FD继承夹具通过，原App没有启停或模型消息。具体数值与完整回执在 `.tmp/linux-entry-20261105/`，不提交原运行资料。

额外沿最终生产 `_descriptor → inspect_client` 路径读取同一原App，得到唯一主进程、19个归属进程且 `unknown=false`。部分进程将命令行改为单个 process title，但并非空白；现有扁平化命令解析仍识别 Chromium 参数，现有父子链也能区分 host/CLI/REPL 工作进程，因此未为这一未复现的问题新增分类分支。这只证明进程身份和管理状态可读，不能据此推定任务空闲或允许退出。

冷态 **元数据识别** 已在实机验证，不等于已对用户原App执行过冷启动/完整私有握手；后者需整合后在即时任务核验与授权范围内单独验收。稳定安装入口的部署也需保留旧Test原资料目录，不能换成临时空资料后宣称升级完成。

## 影响

默认扫描可识别该真实AppImage，安装路径、进程身份与渲染目标不再混淆。新增静态解析只在文件身份变化时发生；运行核验不读取不相关进程的FUSE/NFS文件，只检查当前用户候选映像。代价是其他打包形式、无解析能力的冷态及不同运行时生命期约定不能自动推定支持。

原Test资料目录已从旧进程参数确认；用户级 `.desktop` 的旧版本覆盖现象属于部署入口问题，修复时需正常退出、备份并固定安装位置。此笔记不授权关闭原App或改写账户。
