# Agent Note: 网关在所有客户端停用时保持可管理

Status: implemented

## 问题

关闭最后一个客户端接入后，网关仍需要提供登录和应用管理，以便稍后重新启用客户端。旧页面在从零个已启用客户端重新开启 Codex 时没有刷新聊天；已登录页面首次请求客户端状态前还会并发读取 Codex 列表，停用状态下的正常拒绝被误报为页面错误。未配置 Codex 时，展示开关与服务端默认启用偏好也可能不一致。

## 决策

客户端 `enabled` 展示值使用与写入门相同的持久偏好规则，与安装和账号就绪状态分开。`quitDesktop: false` 仍只撤销网关接入并保留原生 App 与任务；显式退出继续走原有进程和任务核验。全部停用的偏好在网关重启后保持，启动扫描不自动开启任何客户端。

停用后的状态探测、通知跟随及模型刷新统一受启用门约束，并保留已有缓存；具体资源边界和验证见[停用客户端的后台观测](2026-11-06-disabled-client-observation-and-cache.md)。

页面保留认证后的管理入口与无客户端空态。从零个客户端重新开启 Codex 时，即使内部会话视图原本仍指向 Codex，也在启用写入成功后触发一次原有列表选择回调；写入前的乐观开关不会发起这次列表读取。首次 Codex 列表读取继续与客户端发现并行；若发现结果表明没有选择 Codex，则不展示该预读取的停用错误。

## 既有笔记审计

[客户端状态读取避开启动锁](2026-10-14-client-status-startup.md)规定展示快照和写入门分离；本次只统一 Codex 偏好显示，不改变状态刷新或写入核验。[Codex 聊天列表按主机渐进显示](2026-10-16-codex-list-first-paint.md)规定初始列表并发读取；本次保留该顺序，并仅约束无客户端时的错误展示与重新启用后的列表刷新。

## 备选方案

登录时总是等待客户端发现后才读取 Codex 列表可避免停用请求，但会重新拖慢已启用 Codex 的首屏。让空状态强制选择 Codex 可复用旧回调，却会让停用状态与用户选择不一致。

## 测试

Node 回归覆盖最后一个客户端停用后重新启用 Codex 的列表刷新、所有客户端停用时的已认证页面与静默预读取拒绝。Python 回归覆盖展示与默认偏好一致、三个停用偏好持久化、重启后不启动任何客户端。已安装的 Mac 和 Windows Test 均验证三个接入全停用后仍可认证和管理，并恢复原启用偏好；未退出当前 Codex 宿主。Windows 原生 App 在停用接入期间保持运行。基线后端在真实 Windows 上原本已支持全部停用，本次修复的是状态一致性及页面恢复，不将原始 Codex 退出失败的未明原因宣称为已定位。

## 影响

网关在零个客户端接入时仍可登录和重新启用客户端，同时不会把停用 Codex 的正常拒绝显示为故障。首次页面仍可能发出一次并行的 Codex 只读请求；其结果不会授权操作或开启客户端。
