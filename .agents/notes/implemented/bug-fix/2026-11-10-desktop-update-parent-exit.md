# Agent Note: 桌面更新识别已退出但未回收的父进程

Status: implemented

## 问题

本机更新日志记录 2.2.0 首次尝试因“应用尚未退出，更新已取消。”失败，随后一次成功。保留的旧安装控制器已经使用 `app.exit(0)`，不能将该调用当成本次修复。日志没有记录当时父进程状态，尚不能确定历史失败的具体原因。

独立 macOS 子进程夹具证实：子进程退出但尚未被其拥有者回收时，状态为 `Z`，`os.kill(pid, 0)` 仍成功。原更新助手因而将已退出进程当成运行中的 App，等待到超时。

## 决策

POSIX 更新进程查询在 PID 存在时读取 `ps` 的状态；只有明确的 `Z` 状态被视为已退出。查询不可用、超时或未能确定状态时仍按存活处理。父进程等待复用这条规则，保持原有等待期限，不终止目标进程。Windows 继续等待原进程句柄；POSIX 的僵尸进程证据不用于解释 Windows 反馈。

## 备选方案

延长等待期限仍不能解决一个持续未被回收的僵尸 PID。直接忽略 PID 或超时后继续替换，可能覆盖仍在运行的 App，因而不采用。给控制器再次加入 `app.exit(0)` 不产生行为变化；旧安装已包含这一调用。

## 影响

已退出的 POSIX 进程不会继续阻塞更新交接与同模块的进程存活核验。每次查询存活 PID 增加一次有界的本地状态查询；无法取得状态时保持原有保守行为。现存的网关身份核验、正常停止、ACK、回滚及数据目录边界保持不变。

更新助手由旧安装复制运行，因此新版包中的修改无法反向修复旧版负责执行的本次升级。历史 Mac 失败与 Windows 两次更新反馈仍需保留旧版、原启动方式和真实设备验收；本次不执行真实更新或退出正式 App。

## 验证

修复前，隔离的真实 macOS 未回收子进程稳定返回 `Z`，原 `wait_parent` 抛出父进程未退出的超时。修复后，28 个 Python 更新用例全部通过，包含同一真实子进程、仍在运行的父进程和状态查询失败/超时。Node 更新与控制器回归通过 33 项，Windows 路径专项用例在 macOS 跳过 1 项。上述测试不替代 Windows 原生执行与打包安装验收。
