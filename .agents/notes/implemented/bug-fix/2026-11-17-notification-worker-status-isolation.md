# Agent Note: 可重建通知状态不终止后台工作线程

Status: implemented

## 问题

`notification-status.json` 只保存各通道的运行状态，但损坏 JSON、非法编码或错误容器会令状态读取失败。通知 worker 处理原异常时再写错误状态，可能再次抛错并结束线程；桌面读取同一状态也会受到影响。

## 决策

PR194 保留作者提交 `b23a200a25bdb3691abe1e7192c8902bdd94a165`。新增 `read_status_json` 专供可重建状态使用，读取或结构异常时记录警告并采用默认字典；通知通道和桌面状态读取共同使用这一入口。通道记录写入前核验为字典，保留其他通道的有效状态。

三个后台 worker 通过 `_report_worker_error` 报告错误，状态写入本身失败时只记录异常，不再将异常抛出工作循环。共享严格 `read_json` 的账号、配置、密钥及 `notification-delivery.json` 消费者不改用此降级函数；未知投递记录不被清空或重放。

历史笔记审计：[入口提醒损坏恢复](2026-11-17-address-notification-corrupt-state.md)部分重叠，但其 `address-notifications.json` 保存事件去重信息，必须先保留原始证据，不能采用本篇状态显示的空字典恢复。[投递隔离](2026-10-28-notification-delivery-isolation.md)仍决定工作线程与投递账本，本篇只补充错误报告边界。两者均保留，无完全取代记录。

## 备选方案

放宽共享 `read_json` 可以让所有读取统一容错，但会使认证和投递证据错误变成空状态，存在错误授权或重发风险。继续让错误报告抛出异常能暴露失败，却导致工作线程停止；采用局部状态降级及异常日志，同时保持严格账本边界。

## 影响

损坏的显示状态可由后续扫描重建，通知后台循环不再因错误报告二次失败而终止。代价是历史运行状态可能丢失，持续磁盘写入错误仍无法保存新状态；日志与告警保留，不据此宣称通知已经投递。原账号、配置、手机绑定和消息账本不因该恢复被覆盖。

## 测试

集成后 `test_notifications.py` 57 项通过，其中隔离回环 HTTP 测试验证真实请求及重定向约束，新增状态回归覆盖坏 JSON、错误类型、worker 连续执行及 disk-full 报告失败。源码核对桌面调用改用同一 helper；新增测试没有调用完整 `Desktop.snapshot`，也未验证真实桌面通知或手机送达。
