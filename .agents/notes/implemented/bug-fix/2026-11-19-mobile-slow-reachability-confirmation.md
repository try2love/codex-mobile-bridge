# Agent Note: 手机慢连接在超时后做有界可达确认

Status: implemented

## 问题

Issue #218 中，通知读取仍在更新，而首页独立探测先超时并显示未确认。旧电脑条目的无凭据 `/api/auth` 探测只等四秒；有信道目录的条目使用另一条原生身份证明读取链。两条读取与通知的等待时限不同，通知红点更新不能保证更短的独立探测也成功。

## 决策

两端首页可达探测和信道 `/api/connection/prove` 的只读 GET 先采用四秒快尝试，仅在传输超时后继续一次慢确认。两次共用从开始时计算的单调时钟十二秒截止点，慢确认只使用剩余预算。Android 的连接、响应头和每次正文读取都重算剩余时间；iOS 同时设置等待数据和整个资源的超时，第二次资源上限取剩余预算。快尝试超时时不先发布失败，只有最终确认结束后才回传结果。

HTTP 错误、格式无效、明确离线、响应过大及身份签名不符直接失败，不进入第二次请求。信道两次读取仅复用该次新生成的随机 challenge，仍完整校验设备、目标地址与 HMAC；取消和既有页面/绑定代际检查继续阻止旧结果生效。探测不发送 Cookie，不跟随重定向，不改 root 凭据，不重试任何写请求。通用发现、绑定登记、通知同步与聊天请求的等待配置保持原有语义。

本记录与[手机网关信道绑定](../architecture/2026-11-02-mobile-gateway-channels.md)和[优先局域网策略](../feature/2026-11-02-prefer-lan-channel.md)部分重叠，只改变一次读取确认的等待规则，不改变地址授权、信道选择和流量新鲜度规则。没有找到同机制的活跃提案，也没有归档或删除已有决定。

## 备选方案

统一放宽所有请求的超时实现简单，但会扩大写入结果未知的等待与重放风险，因此只改两条只读探测。用通知红点直接判定在线可以减少探测，不过 Android 的 fresh 目前只有布尔状态、没有可复用的到达年龄，iOS 展示快照也没有独立的绑定与时钟证据；本次不把缓存改成实时联网证明。始终只等四秒开销最小，却会继续误判蜂窝与 Tailscale 的慢响应。

## 验证

Android 生产探测在修改前对隔离服务器的 4.3 秒响应返回 false；修改后两端均通过该延迟响应。JVM 与 Swift 的真实 HTTP 夹具覆盖十二秒预算、逐字节慢流、慢确认阶段取消、伪网关、明确离线、重定向、大小与无凭据边界。原生绑定夹具同时覆盖旧身份撤销、新登录、同次 challenge、延迟证明成功、错误设备和错误签名拒绝。

## 影响

快速可达时仍立即显示结果，慢连接可在第二次确认成功后更新状态；持续不可达的确认最多使用十二秒 HTTP 预算，且每个超时地址最多增加一次 GET。测试使用本机隔离服务器和现有 JDK/Swift 编译器，没有安装手机 App、操作真实账号或测试运营商蜂窝网络。
