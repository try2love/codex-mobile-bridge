# Agent Note: Antigravity 停止使准备中的旧消息失效

Status: implemented

## 问题

原生取消可以越过等待响应的发送 RPC，但已进入适配器、仍在读取会话状态或准备指令和模型的旧请求，可能在停止返回后才提交 `SendUserCascadeMessage`。它也可能清除 Hook 停止标记，让用户已经停止的请求重新执行。

## 决策

- `AntigravityCli` 用递增序号记录每个 `(surface, native conversation_id)` 最近一次停止，独立的短锁保护该状态。`stop()` 在取消 RPC 前递增代数，并在同一锁内执行设置 Hook 停止标记的 `before_stop` 回调；不持有 Hook 锁或停止代数锁等待 HTTP。
- 适配器在任何会话解析之前，为显式 `send/goal/compact` 捕获当前停止序号快照，经 `_send_prompt_or_items()` 传到 `send_user_message()`。直接调用 CLI 发送的路径在模型解析前捕获代数。
- CLI 完成模型解析并取得原有普通 RPC 锁后，才在短锁内比较代数。只有目标来源及会话的停止序号晚于入口快照时，旧请求才本地拒绝，不提交原生消息，也不执行 `before_send`。通过检查后执行 `begin_user_turn()` 回调，清除当前会话的 Hook 停止标记；排队内容不自动消费。下一次显式请求捕获新快照，可以正常继续；其他会话的停止不会误取消当前请求。
- 代数锁在调用 HTTP 前释放。原有普通 RPC 锁仍按既有语义串行化正常写入，独立取消 RPC 可以到达原生服务。

已有[Hook 停止记录](2026-11-16-antigravity-late-hook-stop.md)继续负责迟到工具、审批竞态和队列生命周期，二者部分重叠；本记录只补准备中请求的失效规则。没有完全吸收旧记录，也不扩展到其他客户端。

## 备选方案

单用 Hook 的停止布尔标记简单，但显式继续需要清标记，不能区分停止前准备中的旧请求和停止后新请求。只在适配器调用发送前比较代数，改动较少，但后续模型读取和 RPC 锁等待仍可能跨越停止。把停止代数锁一直持有到 HTTP 响应可以消除本地间隙，却会再次阻止取消到达正在等待的发送，因此不采用。

## 验证

- 修改前，初版准备阶段回归的九个组合均错误提交旧请求，不能得到本地停止错误。
- `test_antigravity_stop_generation.py` 五项通过：覆盖 `send/goal/compact` × 本机记录解析、会话、指令、模型准备四个阶段，普通 RPC 锁等待、来源及会话隔离、停止回调顺序，以及等待原生响应时仍可取消。旧队列保留，后续显式请求和工具 Hook 正常。
- `test_antigravity_stop_hooks.py` 八项、`test_antigravity_model_effort.py` 五项通过，分别守住 Hook 生命周期和原生模型参数透传。

## 影响

停止会使同一来源、同一会话中尚在准备的旧请求失效，不取消其他来源或其他会话，也不永久阻止后续用户继续。停止代数只存内存，不改变配置、IPC 或原生消息格式。尚未操作真实客户端。

最终代数检查与 HTTP 请求提交之间仍有原生协议窗口，包含原生端点核验和网络提交；原生服务没有可用于原子比较的停止代数令牌。若停止恰好发生在这一窗口，旧请求仍可能到达原生服务。本改动没有消除所有提交与取消竞态，也不会自动重放未知写入或擅自重试取消。
