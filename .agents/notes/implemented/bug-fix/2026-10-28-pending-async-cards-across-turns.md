# Agent Note: 跨轮次保留尚未回答的异步问题卡片

Status: implemented

## 问题

Codex 桌面可以同时保留多个异步提问。Bridge 的 `async_requests()` 只扫描最后一轮：回复一张卡片触发新轮次后，旧轮次的其他卡片从手机和 Web 消失，虽然原桌面仍待回答。合成桌面 IPC 夹具复现了两个卡片只回复一个后，视图错误返回空请求列表的问题。

## 决策

在原生状态已提供的有序历史中，先按 `questionItemId` 收集已接收的回复，再提取各轮次尚未回答的问题。回复可以来自后续轮次的输入、用户消息或状态为 `accepted` 的转向消息；被拒绝或未接收的转向消息不消除卡片。

每张卡片继续使用原轮次和消息 ID，每个问题继续使用原消息 ID 和索引。仅移除有对应回复的问题，同卡片的其他问题与其他卡片独立保留。普通审批仍走原生请求列表；此修正不把异步问题伪装成原生 RPC 审批，也不增加自动回复或重放。

只读取当前原生快照已有的历史，不为提取卡片自动加载全量历史、激活会话或调用模型。历史未包含的卡片不宣称已恢复。

## 既有记录核对

检索现有活跃笔记的异步问题、卡片及回复标记，未发现记录此轮次筛选决定的笔记。此修正沿用 `ordered_turns()` 的既有普通数组和 canonical 历史解析，不引入另一份历史缓存。

## 备选方案

- 前端暂存消失的卡片能暂时保留画面，但重新打开会丢失，且后端仍会拒绝旧轮次的回复。因此在共享状态规范化层修正。
- 仅向前保留一轮改动较少，却仍会在连续回复多张卡片时漏掉更早的未答问题；按明确问题 ID 跨已有历史核对才符合独立卡片语义。

## 影响

手机、Web、时间线和通知共用的请求投影得到一致的未答集合，不修改页面结构和样式。提取请求需要遍历当前已加载历史，避免只扫描最后一轮带来的漏项；没有引入持久化格式或额外网络请求。

## 验证

IPC 集成用例先证实旧实现返回空列表，再验证修正后第二张卡片保留并能使用原问题 ID 发送回复。canonical 历史用例覆盖后续轮次输入、同卡片部分回答和拒绝／接受转向消息。浏览器夹具覆盖两张卡片各自提交、未答卡片保持可用，以及更新快照后仍能提交另一张。真实用户会话与安装包的验收需单独记录，不用合成夹具替代。

2026-10-29，包含此修正的 `026784022ab5` Test 已在 Mac、Windows、Linux 构建、安装并启动。三端冻结包回归均通过；浏览器夹具在 Chrome 与 WebKit 的宽屏、窄屏四种组合通过。这里确认的是合成 IPC 与浏览器多卡片语义，不声称已代替用户在真实桌面会话中堆积卡片后的人工实测。此次卡片修正只涉及共享请求投影和测试，不改界面样式。

## 原生跳过状态的边界（#133）

上述“已回答”归并不能消除原生界面中仅点击“跳过”的问题。2026-11-07 对本机 Codex `26.1103.31037`（build `25241`）以及 2026-11-08 对已改名为 `ChatGPT.app` 的 `26.1103.41825`（build `25679`）的只读核对均确认，这一动作与提交回复走不同路径：

- 原生问题组件调用 `HAYt._E`，只把当前问题的 `HAYt.TH` 状态更新为 `isSkipped: true`，同时隐藏对应桌面通知。该状态以 `hostId/threadId/entityKey/itemId` 定位，不写入问题回复消息。
- `TH` 使用 `zTeN.bD → jwtq.bD → Nmf8.T` 的 renderer 内存 signal-family；`owner` 只用于内存状态的归属和释放。原生 `Lezo` 从历史重建时仅取得问题与已接受回复，`HAYt.zJ` 在没有既有内存状态时初始化 `isSkipped: false`，没有从历史读取跳过字段。
- 当前安装包的原生 IPC 方法表以及对应处理器没有异步问题跳过的读写或广播方法。`thread-follower-submit-user-input` 调用 `replyWithUserInputResponse`，处理的是有原生 `requestId` 的同步输入请求，不能拿异步问题 ID 代替它。Bridge 当前接收的线程历史也不能据此推断桌面已经跳过某一个问题。

旧版证据定位于安装包 `webview/assets/async/182735.e33af7cdca.js` 的 `HAYt/Lezo/uHDr`。新版对应文件为 `182735.d1916dd704.js`，状态 family 的实现位于 `189497.7105543924.js`；`42793.61ccb40e22.js` 的原生跳过事件仍只调用通知隐藏与 `HAYt._E`。新版 `.vite/build/early-bootstrap.js` 包含 18 个 `thread-follower-*` 操作，没有问题跳过或读取跳过状态的方法。两版的 `Lezo` 都只按已接受回复重建状态，`zJ` 都在新建内存项时将 `isSkipped` 设为 `false`。这些名称只记录核查位置，不作为 Bridge 对其他版本的稳定接口。

因此 #133 的原生双向跳过仍未实现。本轮不添加会伪造回复、触发模型或只清除 Bridge 卡片的“跳过”入口，也不修改原 App、读取或注入 renderer 内存、操作真实用户聊天来绕过该接口缺口。保留现有未答集合比把未同步的局部隐藏宣称为双端一致更符合数据语义。

后续实现必须取得原生可读、可写且有明确完成回执的跳过状态来源，并按接入实例、宿主机、会话及问题 ID 精确归并。需要分别验证桌面跳过、远程跳过、同卡片多个问题、其他未答卡片保留以及重新接入后的状态；仅给 Bridge 夹具添加一个假 `isSkipped` 字段不能证明上游支持。此核对是协议和代码证据，不声称已完成真实双端跳过验收。

## 后续范围调整

用户随后接受先提供网关范围的逐题跳过。[远程逐题跳过](../feature/2026-11-08-remote-question-skip.md) 取代上述不提供局部入口的范围限制；本篇原生 renderer 内存状态、IPC 缺口和不伪造回复的结论仍保留。该新能力不等于原生 App 双向跳过同步。
