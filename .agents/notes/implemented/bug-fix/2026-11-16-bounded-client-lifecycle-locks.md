# Agent Note: 桌面启停的全部锁等待有界

Status: implemented

## 问题

关闭请求的账号操作门锁已有两秒预算，但其前面的客户端锁、客户端写锁以及后面的账号状态锁仍无界等待；显式开启连操作门锁也无预算。因此手机超时后，排队请求可能才启动或退出 App。

## 决策

显式 Codex 开启、停用及退出复用已有有界门锁上下文，覆盖四把锁。每把锁最多两秒，合计排队最多约八秒；超时立刻拒绝本次请求，退出已取得的锁，不留下稍后执行的启停动作。原锁顺序不变，客户端写锁仍由 _changing 更新绑定与读取代数。

明确强制退出同样不无限排队；它仍绕过任务检查，但不能穿过并发账号写入去修改未核验的进程。后台启动调度不改变本次规则。

## 备选方案

仅延长手机超时没有消除延迟退出。先取得账号门锁再取得客户端锁会改变既有顺序并引入死锁。强行释放其他线程持有的锁会破坏正在进行的写事务；均不采用。

## 影响

繁忙时用户得到尚未执行的明确结果，可稍后主动重试。该预算仅约束排队，不把原生启动、退出和任务检查各自的执行预算改成两秒。状态读取已有缓存路径不因该改动清空。

## 测试

持有四种锁后分别发起正常退出、强制退出、开启：12 个子场景有界拒绝，释放锁后也没有延迟执行。修复前七种原有组合会等待到测试预算耗尽。18 项 Codex 生命周期检查通过，另经只读复审；没有退出当前 Mac 对话。
