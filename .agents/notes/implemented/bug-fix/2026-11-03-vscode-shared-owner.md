# Agent Note: 独立配置的手机与 VS Code 共用原会话

Status: implemented

## 问题

Issue #106 的 Windows 用户观察到，同一目录的普通盘符路径和带 `\\?\` 的路径让原 owner 身份校验失败，另起 daemon 后再打开编辑器会遇到写入占用。当前扩展提供原生 follower；网关显示的功能此前只依赖保存历史中的来源，即使已经连接编辑器也隐藏了消息编辑、分支、侧边聊天和目标。

## 决策

Bridge 先确认原配置、host、会话 ID、provider、cwd 和实际 owner，再使用与 Codex App 相同的跟随协议。Windows 本机的目录别名采用已有的文件系统同一性检查，在连续 patches 中复用上一帧已验证的 cwd。SSH 和非 Windows 主机保持严格比较。其他客户端发来的旧协议帧不能使健康会话丢失连接。

跟随已确认的本机 VS Code owner 时复用聊天编辑、分支、侧边聊天、目标、原生历史和设置。独立配置的元数据进程沿用该 home；分支只在支持 `threadSource` 的本机运行时创建，临时侧边会话使用独立存储。未知 owner 或用户的发送请求不会启动备用 daemon。编辑器已退出且归属探测确认缺席后，主动继续可接续原 ID；释放保留既有取消订阅语义。

## 备选方案

保留原先的 IDE 超时接续可以在原生路由不响应时更快进入无头会话，但超时无法证明编辑器已经交还写入权。为每套配置另起一个 Codex Desktop 则无法同步 VS Code 当前正在进行的回合。两者都不能满足双端操作原会话的要求。

## 影响

Mac 实测使用临时 VS Code 用户目录、Codex 扩展 26.1021.22027、独立 CODEX_HOME 和只监听回环的合成上游。手机侧与原 VS Code 两端的发送在同一线程可见。VS Code 发起的测试任务通过网关按原 turn ID 中止。两端显示同一条无害命令审批，网关用原卡提供的取消选项处理后，编辑器卡片消失。原生历史与目标读取、独立目录分支、临时侧边聊天创建与关闭也已实测。正常退出编辑器后，被动读取未接管，明确继续才恢复 daemon，随后取消订阅并正常停止专用服务。

Windows 本机的旧扩展 26.602 采用 v7 流且缺少当前 owner 发现与跟随方法，不能据此宣称它具备新版双端同步能力。Windows 的目录同一性合同、未知归属和旧协议的隔离都有定向回归。上述 Mac 真实扩展验证不能替代 Windows 原 App 验收。

本决定修订[独立客户端管理](../feature/2026-11-02-independent-codex-management.md)中关于 IDE 探测超时的接续策略，沿用[独立配置接入](../feature/2026-11-01-independent-codex-home.md)及[共享客户端外壳](../architecture/2026-11-02-shared-client-shell.md)的入口隔离。
