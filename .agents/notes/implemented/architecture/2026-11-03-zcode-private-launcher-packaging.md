# Agent Note: Mac Test 的 ZCode 私有管道启动器与网关签名绑定

Status: implemented

## 问题

Launch Services 能保持原 App 的系统身份，但不会把网关的 3、4 号文件描述符交给 Electron 的调试管道。另一方面，只检查 Unix socket 的用户身份，会让其他同用户程序也能向启动器索取原生控制权限。

## 决策

Mac Test 在外层 App 内嵌一个仅由系统后台启动的子包。独立的已签名网关进程持有管道，启动器只接受网关指定并重新验签的 ZCode 3.17.2。启动器在一次性请求与 socket 的所属用户、权限、对端进程审核令牌、实际映像和代码签名均匹配后传递两枚描述符，在原 PID 执行 ZCode。用户无需另行安装辅助应用。

先完成网关二进制签名，再把最终各架构的 CodeDirectory 摘要封存在启动器的 Info.plist，最后签启动器与外层 App。Mac Test 的构建可显式调用 prepare 和 verify 两步。正式构建尚未固定最终签名顺序，因此暂不装入启动器；应用不能把普通安装或现有的辅助功能 helper 视为私有管道可用。

## 备选方案

直接把带参数的子进程当作正常 App 启动无法证明 Launch Services 身份。只匹配进程名、用户或 bundle 标识也无法区分其他位置的同名程序。对第三方 ZCode 固定单机 CDHash 会排除同一受支持版本的其他正式架构；这里验证已验收版本、官方 Developer ID、安装路径与执行文件。

## 影响

定向签名夹具确认同一 Test 包内的网关可完成对端身份检查，复制到其他位置的同一二进制被拒绝，打包后替换网关二进制也无法通过原摘要验证。裸启动没有请求时立即结束。夹具用临时目录、自有签名与 Unix socket，未操作真实 ZCode。锁屏启停及原生会话接入由功能验收单独覆盖。
