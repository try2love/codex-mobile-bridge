# Agent Note: 上游共享中继与云 HTTP 转发分别校验

Status: implemented

## Problem

共享中继与账号云服务都调用 `relay.protocol.validate`，但两者要求不同。上游共享中继按方法、客户端和操作限定转发；Noise/P2P 与账号 Web 已依赖通用 HTTP 转发，由网关处理业务权限。合并两套实现后，云网页的新建项目、独立客户端与未来写方法会在到达网关前被共享中继拒绝。

## Decision

上游 `main` 的 `216ee1ce`（v2.2.1-preview.1）通过普通双亲合并进入本分支，保留 fork 的云服务、P2P 和开发热刷新接入点。冲突采用上游行为；许可证、版本、Antigravity 与 CLI 更新沿用上游内容，不以恢复云功能为理由覆盖上游实现。

`relay.protocol.validate` 与上游函数保持一致，只服务共享中继。`relay.server` 将操作不允许映射为 HTTP 403，已登录手机不会因此被判为认证失效。相关共享中继、置顶和归档回归沿用上游的允许与拒绝断言。

`relay.http_framing.validate_http_request` 持有云链路已有的相对路径、HTTP 方法 token、正文长度和 GET/HEAD 无正文校验。`cloud_connector` 的 Noise/P2P 请求与 `cloud_web` 调用它，不按 API 名称或客户端维护操作表。未知接口、能力与业务权限继续由原 HTTP 处理器判断。

这次职责分离不新增流量限制、配置开关、重试或失败回退。认证、Origin/CSRF、设备密钥批准、账号和电脑归属、撤销、凭据隔离、Range、未知写入不重放与原有流量限制各归原模块。云页面的 `/cloud-web.js` 继续是明确列出的公开资源，静态资源测试同时保留上游新增资源和这一接入点。

## Alternatives considered

- 全部调用上游 `validate`，能保持最小实现和单一入口，也直接覆盖上游的共享中继回归；但云服务的通用写方法、项目和独立实例请求被拒绝，不能保留已有云链路能力。
- 全部恢复 fork 的通用校验，能让所有转发保持同样的 HTTP 行为，也避免维护共享中继操作表；但会覆盖上游共享中继的操作限制与拒绝回归，不符合上游优先的合并要求。

分别调用两套已有语义，避免把一方的操作权限强加给另一方。共享中继的许可表仍由上游维护，云链路不增加另一份业务表。

## Consequences

共享中继获得上游更新，云网页与 Noise/P2P 保留通用 HTTP 能力。两种入口分别有允许和拒绝回归，后续合并能够核对上游函数而不覆盖云服务。

代价是维护者必须区分调用方的授权主体；共享中继的新操作仍依赖上游许可表，不能直接把云校验函数用于共享中继。两套入口不代表两份业务权限实现，实际账号、设备、实例与文件操作仍在网关校验。

源码与合成浏览器验证不证明真实账号登录、原生客户端联调或手机行为。本次不构建、签名、安装、部署云服务或发布，也不把此前 v2.2.0 的实机证据用于 v2.2.1-preview.1。
