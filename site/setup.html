SETUP / 连接配置

把每一步，连起来。

选好访问方式，照着图示和步骤配置。每一步都说明在哪操作、需要什么权限，以及看到什么才算成功。

准备开始：先在工作电脑打开 Codex App 和网关，确认本机或局域网可以登录。文中的固定隧道入口、内置 cloudflared 与分步 SSH 设置属于尚未发布的本地预览版；请先确认已安装版本具备对应选项。目前公开下载的版本未更新。

局域网 只在同一网络使用 临时 HTTPS · 推荐 没有服务器，也没有域名 Tailscale · 源码预览固定 HTTPS，无需服务器 Cloudflare 固定域名 · 进阶 有域名，希望少管服务器 自有服务器 + SSH · 进阶 有公网服务器与 HTTPS 入口 NAS / Docker · 进阶 已有 NAS / HTTPS 反代

安装软件、调整 SSH 和防火墙等管理员操作由你或管理员在服务器手动执行。App 不接收 sudo 密码；网页上的“复制”只复制文本，不会执行命令。

02
手机 · 浏览器

手机连接同一个可互访网络

用手机打开 App 显示的地址或扫码登录。不要在手机输入 localhost 或 127.0.0.1，那表示手机自己。访客 Wi-Fi、AP 隔离和单位网络策略可能阻止设备互访。

确认结果：能登录、读取聊天；在自己的测试聊天中发送一条消息并收到回复。

临时 HTTPS：不用准备服务器

推荐个人快速接入：无需域名和服务器，配置最少、上手最快。网关与隧道进程持续运行且连接正常时，通常可以沿用当前地址；Cloudflare 不保证永久占用或持续可用。隧道重建导致地址变化后，启用“每次启动网关及入口变化时发送地址”并配置好通知渠道，即可接收新地址；送达时间取决于网络与通知服务。

适合先体验外网访问，可以接受地址变化。

Cloudflare · 规则

让 HTTP 自动跳转到 HTTPS

进入域名的“规则 → 概述 → 创建规则 → 重定向规则”，选择自定义筛选表达式。下面仅匹配网关子域名；请替换示例域名。

(http.request.full_uri wildcard r"http://codex.try2love.com/*")

URL 重定向类型选“动态”，目标表达式如下；状态码选 301，勾选“保留查询字符串”，校验通过后部署。

concat("https://codex.try2love.com", http.request.uri.path)

确认结果：打开 http://codex.try2love.com 会自动变为 HTTPS，再显示登录页。已经打开的 HTTP 登录页需重新打开。

04
工作电脑 + 服务器管理员

准备能登录的普通 SSH 用户

已有可登录的普通用户就直接使用，不必创建专用账号，也不必授予 sudo。先在工作电脑终端验证登录，退出后再填 App。首次连接的主机指纹应与服务器控制台或管理员提供的结果核对。

ssh -p 22 try2love@203.0.113.10
只有 root 账号，怎样准备普通用户？

Ubuntu / Debian 管理员可执行下面命令创建账号。按提示设置账号密码；这不会自动给新用户 sudo 权限。不要为方便登录而全局启用 SSH 密码认证。

sudo adduser try2love

服务器已允许密码登录时，先验证该普通用户能正常登录。服务器仅允许密钥时，按下一项安装公钥。其他系统请由管理员使用该系统的用户管理方式创建账号。

服务器只允许密钥登录

已有可用私钥就直接使用。需要新建时，在工作电脑运行 ssh-keygen，按提示保存到一个新的文件名，避免覆盖已有密钥；建议设置私钥口令。

ssh-keygen -t ed25519

将生成的 .pub 公钥交给管理员追加到该用户的 ~/.ssh/authorized_keys。私钥保留在工作电脑。以下是 Ubuntu / Debian 默认 /home/try2love 家目录的示例；已有文件只追加，不覆盖。

sudo install -d -m 700 -o try2love -g try2love /home/try2love/.ssh
sudoedit /home/try2love/.ssh/authorized_keys
sudo chown try2love:try2love /home/try2love/.ssh/authorized_keys
sudo chmod 600 /home/try2love/.ssh/authorized_keys

在 App 选择“本地私钥”，选没有 .pub 后缀的私钥文件；设置过口令时同时填写口令。不要把私钥或密码放到公开配置和截图中。

确认结果：工作电脑能以普通用户登录服务器。服务器 SSH 密码与手机网关登录密码是两套凭据。

05
服务器 · 管理员检查与配置

允许这个用户建立反向隧道

已允许转发时可以沿用现有配置。需要调整时，让管理员检查现有 sshd_config、Include 文件、Match 条件及公钥限制，再为目标用户添加或调整以下规则；不要覆盖整个 SSH 配置。

Match User try2love
    AllowTcpForwarding remote
    GatewayPorts no
    PermitListen 127.0.0.1:18787
Match all

AllowTcpForwarding remote 允许反向转发；PermitListen 限制监听地址；GatewayPorts no 保持回环监听。已有 DisableForwarding yes、较早匹配的规则或 authorized_keys 的 restrict / no-port-forwarding 仍可能阻止转发。

sudo sshd -t

语法检查无输出且退出码为 0 才继续。Ubuntu / Debian 通常使用下面的 ssh 服务；其他系统先确认实际服务名。保留当前 SSH 终端，并在新终端再次验证登录。

sudo systemctl reload ssh

确认结果：新终端登录正常。真正的转发权限还需在第 7 步启动 App 隧道后验证。

服务器或管理面板 · 管理员

配置 HTTPS 入口：选择你的情况

四种路径选一种即可。上游始终是 SSH 服务器自身的 http://127.0.0.1:18787；不是工作电脑的局域网 IP。

A · 全新 Ubuntu / Debian，没有网站

确认 80/443 未被现有服务占用，且未安装 Caddy，再由管理员按官方软件源安装。一次运行一条命令，失败时先处理错误。安装 Caddy 后会创建并启动系统服务。

sudo apt update
sudo apt install --yes debian-keyring debian-archive-keyring apt-transport-https curl gnupg
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/gpg.key | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list

先备份再编辑 Caddyfile。把演示域名改为自己的域名；新安装文件中的示例 :80 站点可替换为下面的站点块。若文件已有真实网站，转到路径 B。

sudo cp -a /etc/caddy/Caddyfile /etc/caddy/Caddyfile.before-codex-$(date +%Y%m%d%H%M%S)
sudoedit /etc/caddy/Caddyfile

codex.try2love.com {
    reverse_proxy 127.0.0.1:18787 {
        header_up Host {http.request.host}
        flush_interval -1
    }
}

sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy

只有 validate 成功后才 reload；最后应显示 active。Caddy 自动申请和续期证书，并处理 HTTP → HTTPS。

已有 Caddy

在实际使用的 Caddyfile 或已被 import 的站点文件中添加以下站点块。原有站点保持不变，确认未为同一域名重复定义站点。

已有 Nginx

先用现有证书工具或面板为网关域名配置有效 HTTPS 证书与 HTTP → HTTPS 跳转。将以下 location 放入该域名的 HTTPS server 块；如果已经有 location /，只调整该站点，不重复添加。这里不包含证书签发步骤，不能直接当成完整 Nginx 配置文件。

location / {
    proxy_pass http://127.0.0.1:18787;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}

sudo nginx -t
sudo systemctl reload nginx

仅在 nginx -t 成功后重新加载。Caddy/Nginx 若由面板或容器管理，应使用其现有配置和重载方式，不另建 systemd 服务。

C · 宝塔、1Panel 或其他网站面板

在现有面板中新建独立域名站点或反向代理条目，保留其他站点。不同版本菜单名称不同，逐项对应下面的字段即可。

面板设置 内容
域名 codex.try2love.com
上游协议与地址 HTTP · 127.0.0.1:18787
发送给上游的 Host 原始访问域名 codex.try2love.com
SSL / HTTPS 为此域名申请有效证书，启用 HTTP 跳转
缓存与流式响应 关闭代理缓存、关闭响应缓冲

如果面板反代运行在容器中，127.0.0.1 指向容器自己，可能不是 SSH 服务器。让管理员确认网络命名空间与安全可达的上游，不要为了连通而把 18787 暴露到公网。

D · 其他系统、Docker，或没有管理员权限

其他 Linux 系统按 Caddy 官方安装页选择对应包管理器，后续域名、上游和验收步骤相同。不要在 Rocky / AlmaLinux 等系统照抄 apt 命令。Windows 服务器不在这份 Linux 命令教程范围内，请由管理员提供等效的 SSH 与 HTTPS 服务。

已有 Linux Docker Engine 时，可使用 App“导出手动配置参考”中的 Caddy Compose 方案。仅在 80/443 空闲时启动，保留证书卷；该方案使用 host 网络，必须与 SSH 服务在同一 Linux 主机。Docker 不是绕过管理员权限的方法。

没有管理员权限时，将第 2—6 步交给管理员完成。你只需普通 SSH 用户和允许的转发端口，不需要申请 sudo 权限。App 的“复制服务器检查 Prompt”可先让服务器内的 Agent 只读检查，不能代替管理员授权。

服务器 → 工作电脑 → 手机

按顺序验收，不跳步

什么时候需要 Docker 中转？

NAS 已能直接反代到电脑时，不需要再加 Docker。只有确实需要中间 HTTP 转发时，才使用 App 导出的 NAS 部署包。

该包的容器提供 HTTP 中转，不能独立代替 NAS 的证书和公网 HTTPS。若外层反代运行在宿主机，上游可用 http://127.0.0.1:18787；若它也在容器中，127.0.0.1 指向该容器自己，需按部署包说明设置可达的 NAS 地址并限制访问。

Docker 操作由有权限的用户自行完成。先查看导出包中的部署说明，核对端口和网络，再运行配置检查；不要为了本教程修改其他容器或公开内部端口。
